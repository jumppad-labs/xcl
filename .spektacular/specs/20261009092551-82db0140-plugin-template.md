## Overview

Plugin authors start a new xcl plugin by copying the examples by hand, so there is no working, idiomatic starting point. This spec publishes the standard plugin layout as a ready-to-use template: a plugin with one resource that builds, tests and applies straight away, runs both inside an application and as a separate program, and publishes signed releases for every platform that the GitHub Releases registry can install.

## Requirements

- [ ] **A ready-to-build starting plugin**
  Plugin authors can create a new plugin from the template that builds, passes its tests and applies its sample configuration with no changes.
- [ ] **Runs in-process and as a separate program**
  The plugin created from the template can be used both registered inside an application and run as a separate plugin program.
- [ ] **An explicit change decision**
  The template's provider defines its own decision between update and replace, with the settings that need a replace visible and easy to edit, rather than relying only on the built-in default.
- [ ] **Updates work only from what they are told**
  The template's in-place update acts only on the changed settings and dependencies it is given, without extra calls to rediscover the resource's previous state.
- [ ] **How to build, test and register it**
  The template's README shows authors how to build, test, regenerate test doubles, release, and register the plugin both in-process and as a separate program, with one command for each of these tasks.
- [ ] **A standard plugin layout**
  The project defines one standard layout for a plugin: where entity types, providers, the backend client and its test doubles, and the plugin's entry points live. The template and the documentation follow it.
- [ ] **Entity types stand alone**
  An application that reads resources of a plugin made from the template can use the plugin's entity types without depending on its providers or on its backend's libraries.
- [ ] **Consistent file order**
  In the template, every file follows the file order the standard layout defines.
- [ ] **Tests in the project's style**
  The template includes unit tests of its provider against a strict test double, including the change decision and the in-place update. It also includes an end-to-end test that applies the sample configuration, confirms the next plan reports no changes, and destroys it.
- [ ] **Checked on every change**
  The template repository builds, runs static checks and runs its tests automatically on every change.
- [ ] **Signed releases for every platform**
  Tagging a version of a plugin made from the template publishes a release with the plugin built for each supported operating system and architecture, with checksums and a signature, in the format the GitHub Releases plugin registry installs from.
- [ ] **Kept up to date with the project**
  The template repository is part of the project's registered repositories, so later changes to the plugin contract are planned and made in the template too.
- [ ] **Documentation shows the standard and the template**
  The project's guides and the documentation site explain the standard layout and how to start a plugin from the template, build it, release it and install it.

## Constraints

- **Delivered as a GitHub template repository.** Authors start from it with "Use this template" or `gh repo create --template`, not from a generator.
- **One template for both ways of running.** A single template serves in-process and separate-program plugins; there are no two variants.
- **Public members first in every file.** In every source file in the template, exported types and methods are kept together at the top, ahead of unexported helpers.
- **The template's sample needs no external service.** It builds, tests and applies with nothing else running, while still showing a backend client behind an interface with a test double.
- **Tests follow the repository rules.** testify `require`, Mockery for test doubles, no table-driven tests, and positive and negative cases in separate test functions.
- **Entity types live in a package named `entities`.**
- **The plugin contract doesn't change.** The template and the example's rebuild use the contract as it is today.
- **Built to the standard plugin layout.** The design `plugin-layout.md` (source `design`) settles the plugin layout, what each part holds, file order, the explicit change decision, updates from what they are told, and the test shape. The template, the plugin example and the docs build to it.
- **Releases are GPG-signed.** The template's release signs every release with a GPG key supplied to the release automation; unsigned releases are not published.

## Acceptance Criteria

- [ ] **A new plugin builds and applies out of the box**
  A repository created from the template, with nothing changed and no external service running, builds, passes all its tests, applies its sample configuration, then plans with no changes, then destroys cleanly.
- [ ] **The same plugin runs in-process and as a separate program**
  Following the README, the plugin created from the template applies its sample configuration both when registered inside an application and when run as a separate plugin program.
- [ ] **Editing a setting that needs a replace replaces the resource**
  Changing a setting the template marks as needing a replace makes the plan show the resource replaced, and changing any other setting makes it show the resource updated. The template's unit tests exercise both outcomes.
- [ ] **The update acts only on what it is told**
  The template's unit tests drive its update against a strict test double that allows only the calls the reported changes require. A call made to rediscover previous state fails the test.
- [ ] **The README covers the whole workflow**
  Following only the README, an author can build, test, regenerate the test doubles, release, and register the plugin in-process and as a separate program, each with a single command, and every command shown succeeds.
- [ ] **The standard layout is written down**
  The project's guides describe the standard plugin layout, and the template matches it, with every location the guide names present.
- [ ] **The template's entity types stand alone**
  An application reading the template's sample resources from state builds without the template's providers or backend libraries.
- [ ] **Files list public members first**
  In the template, every source file shows its exported types and methods before any unexported helper, and provider methods appear in the lifecycle order the standard layout defines.
- [ ] **The template checks itself**
  A change pushed to the template repository runs a build, static checks and the full test suite, and a failure in any of them is reported on the change.
- [ ] **A tagged release is published and signed**
  Pushing a version tag to a repository created from the template, with its signing key configured, creates a GitHub release holding a binary for each supported platform, a checksum file and a GPG signature, with no manual steps; the signature verifies against the published public key.
- [ ] **The template is a registered project repository**
  The template repository appears in the project's registered repositories, with a description, and planned work can target it.
- [ ] **The documentation site covers the template**
  The documentation site has a page explaining the standard layout and how to start, release and install a plugin from the template, and the site builds.

## Technical Approach

- The explicit `Changed` answers replace for settings matched with `change.Within`, or for a replaced dependency the resource is built on; otherwise it answers update when anything changed; otherwise it defers to the default.
- The template's sample resource is backed by a simple local implementation of its client interface, such as files on disk, so it runs with no external service.
- CI runs on GitHub Actions.
- The template repository is created and registered with the project at the start of implementation, so the plan can attribute work to it.
- The signing key is held as a repository secret.

## Success Metrics

- **Time to a first plugin.** A new author following only the README reaches a working plugin of their own in under 15 minutes.
- **First real resource without guessing.** An author can add their own resource by following the README and the layout guide alone, without reading the plugin examples or xcl's source.
- **The template stays current.** The template's checks pass against the latest xcl release.
- **One shape everywhere.** The template and the documentation never disagree about the layout: checked against the layout design, neither has a part in a place the design doesn't name.

## Non-Goals

- **An in-process vs external parity test in the template**, one running the same scenario in-process and as a separate program and comparing the results. The template carries unit, end-to-end and CI checks only.
- **A hosted plugin registry or marketplace.** Installing plugins from GitHub releases is covered by the GitHub Releases plugin registry spec; a hosted registry or marketplace is out of scope.
- **Porting jumppad's resources.** This spec defines the layout jumppad's resources will take, but porting any of them to xcl plugins is later work.
- **Jumppad's engine-level behaviour.** For jumppad, whose resources will later be ported to this layout, the implicit image cache and registry merging have no plugin equivalent here; a port decides them separately.
