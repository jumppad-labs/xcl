# Feature: 20261016064106-8931613a-python-encode-entity

## Overview

Python programs that embed xcl can't yet do something Go programs can: turn an entity they hold into xcl configuration text. This holds both for entities read back from a configuration and for ones the program builds itself. This feature gives Python the same capability with the same choices Go offers:

- include the fields a provider filled in
- include empty fields
- show real secret values
- show references as they were written
- colour the text for a terminal

It also gives the existing way of rendering a saved record those same choices. The rendering is done by xcl's shared engine, not reimplemented in Python, so Python and Go programs get identical text for the same entity. xcl's Python guide and API reference are updated to match.

## Requirements

- [ ] **Encode a looked-up entity**
  Python users can turn any entity returned by a lookup on a configuration (by address, by type, the single entity of a type, all entities of a class, every entity, or the entity carried by an event) into xcl configuration text. Every capability in this spec, including hand-built and untyped entities and the saved-record changes, is offered by both the synchronous and the asyncio API.

- [ ] **Encode a hand-built entity**
  Python users can turn an instance of a registered class that they built themselves, never read from a configuration, into xcl configuration text, with the same four encoding choices and highlight as a looked-up entity.

- [ ] **Encode an untyped entity**
  Python users can encode the generic entity a lookup returns for a plugin type that has no registered class.

- [ ] **Same text as Go**
  For the same entity and the same choices, the text Python produces is identical to the text Go's encoder produces.

- [ ] **Include computed fields**
  Users can choose to include the fields a provider filled in. By default those fields are left out.

- [ ] **Include empty fields**
  Users can choose to include attributes that are unset or at their zero value, written the way Go writes them. By default they are left out.

- [ ] **Reveal sensitive values**
  Users can choose to show the real value of each sensitive field. By default each sensitive value is shown as the sensitive marker. For an entity that came from a lookup, the real value is shown even though the looked-up instance holds only the marker, as Go shows it. For a hand-built entity, the value it holds is shown.

- [ ] **Show references**
  Users can choose to write each field that referred to another entity as it was written in the configuration, instead of its resolved value, following Go's rules for sensitive fields. A hand-built entity has no references, so its values are written as they are.

- [ ] **Highlight**
  Users can choose to colour the text for a terminal, with the same colouring the existing saved-record call uses. Highlight combines with each of the four encoding choices.

- [ ] **Changes to a looked-up entity are kept**
  When a user changes a field on a looked-up entity and then encodes it, the text shows the changed value. When revealing, an edited sensitive field shows its edited value; an unedited one shows the configured value.

- [ ] **Saved records get the same choices**
  The existing call that renders a saved record accepts the four encoding choices (computed, empty, reveal sensitive, show references) alongside highlight. Calls that pass none of them behave exactly as today.

- [ ] **Failures raise the existing errors**
  Encoding fails with xcl-python's existing exceptions and returns no text for each of: a variable, an output, a module, an object that isn't an entity, a value with no configuration form, and an instance of a class the configuration did not register.

- [ ] **Parity record, docs and design updated**
  xcl-python's parity record lists entity encoding as supported rather than not applicable. Its README and xcl.dev's Python guide and API reference describe the new call, the four encoding choices and highlight, and the saved-record changes. The shared-library design document lists the new call and the saved-record call's new choices.

## Constraints

- Rendering must be done by xcl's shared engine through the core service, not reimplemented in Python. Python's own code is limited to what only Python can do: turning a Python instance into the record the engine reads and passing the choices through.
- Must be built to the settled shared-library design in the `design` source at `libxcl.md`: calls are core-service messages, entity data crosses as JSON bytes, and encoding is a lookup with the lookup rules, so it is refused while an operation runs.

## Acceptance Criteria

- [ ] **Looked-up entity encodes**
  Given a configuration with a resource that has a subtype and one without, encoding the entity returned by each kind of lookup (address, type, single of type, all of class, every entity, event entity) returns one block headed `<type> "<subtype>" "<name>"` or `<type> "<name>"`, through both the synchronous and asyncio APIs.

- [ ] **Hand-built entity encodes**
  An instance of a registered class, built in Python and never loaded, encodes to the same text as the same entity loaded from a file with identical values.

- [ ] **Untyped entity encodes**
  An entity of a plugin type, returned as the generic entity because no class was registered for it, encodes to a block of that type with its fields.

- [ ] **Text matches Go**
  xcl-python's parity fixtures compare Python and Go output for the same configurations. For each entity they cover (looked-up, hand-built and saved records) and each combination of the four encoding choices, the Python text is byte-for-byte equal to Go's encoder output for the same entity and choices.

- [ ] **Computed fields default out, opt in**
  For an entity with a provider-filled field, the text leaves that field out by default and includes it when computed fields are asked for.

- [ ] **Empty fields default out, opt in**
  For an entity with an unset optional string, a nullable attribute left out, a list left unset and an unset map, the text omits all four by default. When empty fields are asked for, it writes the string as `""`, the list as `[]`, the map as `{}`, and the nullable attribute as the zero value of the type it holds, as Go does. A list the configuration sets to `[]` is written as `[]` with or without the choice, as Go writes it.

- [ ] **Sensitive masked by default**
  A looked-up entity with a sensitive field shows the sensitive marker for that field when reveal isn't asked for.

- [ ] **Sensitive revealed for a looked-up entity**
  With reveal asked for, the same looked-up entity shows the real configured value, although the Python instance itself only held the marker.

- [ ] **Sensitive revealed for a hand-built entity**
  With reveal asked for, a hand-built instance shows the value its sensitive field holds. Without reveal, it shows the marker.

- [ ] **References shown**
  For a looked-up entity whose field was written as a reference to another entity, the text shows the resolved value by default and the reference as written when references are asked for. A sensitive field written as a single bare reference shows the reference. One written any other way shows the marker unless reveal is also asked for.

- [ ] **References on a hand-built entity**
  With references asked for, a hand-built instance encodes to the same text as without, and doesn't fail.

- [ ] **Highlight combines**
  With highlight asked for, the text contains terminal colour codes. With the codes stripped, it equals the uncoloured text for the same choices. The coloured text equals the saved-record call's coloured text for the same entity and choices.

- [ ] **Edited looked-up entity**
  After changing a non-sensitive field on a looked-up entity, the text shows the new value. After changing a sensitive field to a new value and asking for reveal, the text shows the new value, not the configured one.

- [ ] **Saved records accept the four choices**
  A saved record encoded with each of the four choices produces the same text as encoding the live entity with the same choices. A saved-record call with no choices returns exactly the text it returns today.

- [ ] **Errors**
  Encoding each of the following raises xcl-python's existing exception for that case and returns no text: an object that isn't an entity, a variable, an output, a module, a value with no configuration form, and an instance of a class the configuration did not register.

- [ ] **Refused during an operation**
  Encoding, by either call, while an operation is running on the configuration raises xcl-python's existing error for a lookup during an operation and returns no text.

- [ ] **Parity record and docs**
  xcl-python's parity record lists entity encoding among the supported calls and no longer under "not applicable". Its README and xcl.dev's Python guide and API reference each show the new call, name the four encoding choices and highlight, and mention the saved-record call's new choices. The shared-library design document lists the new call and the saved-record call's new choices.

## Technical Approach

- Prefer one new core-service call for encoding an entity, taking the entity record and the choices, and adding the same choices to the existing saved-record call. Both should go through the engine's existing single rendering path, so identical text comes for free.
- Keep colouring where it is today: the engine applies the existing terminal highlighting after rendering, as the saved-record call already does.
- Prefer that, for a looked-up entity, the engine fills a sensitive field that still holds the marker from its own copy of that entity, found by its address, when reveal is asked for. A hand-built entity has no copy to fall back on.
- On the Python side, prefer an encode method on both configuration classes that sits beside the saved-record call, with keyword choices matching its style (all off by default). The class-to-name lookup resolves through the configuration's own registrations, as the lookups do.
- Keep the Python instance-to-record step as the mirror image of the existing hydration, reusing the class registrations and field metadata already used to build schemas, rather than a separate serialiser with its own rules.
- The design document to update is the Lookups section of `libxcl.md`.
- Known risk: if the record built from a hand-built instance differs from what the engine expects (labels, meta, nullable and sensitive fields), the text won't match Go. The parity fixtures are the guard.

## Success Metrics

- 100% of the parity fixtures produce byte-identical text from Python and Go for every combination of the four encoding choices, for both a looked-up entity and its saved record.

## Non-Goals

- Compatibility of the core-service messages with older clients. xcl is unreleased, so breaking changes to those messages are fine, and no effort goes into keeping older clients working against the new engine.
- Exposing entity encoding through any binding other than Python.
- Changing what Go's encoder writes, its choices, or its defaults. Python matches Go as it is.
- Encoding several entities in one call. As in Go, a caller encodes each entity separately.
- Reading the encoded text back into a Python instance. Turning xcl text into entities stays with the existing load.
