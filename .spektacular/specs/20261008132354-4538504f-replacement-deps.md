# Feature: 20261008132354-4538504f-replacement-deps

## Overview

When a configuration change can't be applied in place, such as moving a network to a different address range, xcl today quietly treats it as a small update. The real resource never changes, and anything built on top of it is left attached to something stale. This change lets each plugin say that a change needs the resource rebuilt from scratch, and tells every resource that depends on it what is about to happen, so each can decide whether it also needs rebuilding or just an update. Applying then tears down and rebuilds exactly what needs it, in a safe order, and plans show ahead of time what will be rebuilt and why. Plugin authors get a way to express changes their resources can't take in place, and anyone applying configuration gets real infrastructure that matches what they wrote.

## Requirements

- [ ] **Plugins can say a change needs a rebuild**
  When asked whether a resource has changed, a plugin can answer that it is unchanged, that it needs updating in place, or that it must be replaced: destroyed and created again.
- [ ] **Resources learn what will happen to what they depend on**
  When asked whether a resource has changed, its plugin is also told which of the resources it directly references will be updated or replaced by the same apply, and which of the two each one is. Dependencies that won't change are not listed.
- [ ] **Each resource decides its own outcome**
  A resource whose dependency is being updated or replaced gets the outcome its own plugin decides: unchanged, update or replace.
- [ ] **Decisions follow dependency order**
  A resource's outcome is decided only after the outcomes of everything it depends on are known, so every resource is told about its dependencies' final outcomes.
- [ ] **Applying replaces resources safely**
  On apply, every resource being replaced or removed is destroyed before anything is created, dependents before what they depend on. Replaced and new resources are then created, and updated resources updated, in dependency order.
- [ ] **Nothing changes until every decision is made**
  Applying decides the outcome of every resource before it creates, updates or destroys any of them.
- [ ] **Plans show replacements and why**
  A diff or plan marks each resource that will be replaced as a replacement. When the replacement comes from a dependency being replaced, it names that dependency. The values a replaced or updated dependency will only know after the apply are shown as unknown.
- [ ] **A failed replacement is recorded honestly**
  If a replacement's destroy or create fails, the resource is recorded as failed, so the next apply replaces it again rather than treating it as up to date.
- [ ] **External plugins can decide replacements**
  Plugins that run as separate programs can make and receive the same decisions as plugins built into the program.
- [ ] **Every plugin in the repository uses the new decisions**
  Every plugin shipped in the repository, including the examples and the test plugins, answers with unchanged, update or replace.
- [ ] **The plugin example replaces its network and container correctly**
  In the plugin example, changing the network's address range replaces the network and the container attached to it, and updates the template that reads from them. The real Docker network ends up with the new address range.
- [ ] **The example ships a configuration that shows it**
  The plugin example includes a second configuration, kept apart from its main one, that changes the network's address range. Its documentation uses it to show a plan and an apply that replace the network and container. Today a second configuration sits beside the main one and is read with it, so the main configuration fails to apply; afterwards the main configuration applies on its own again.
- [ ] **Documentation explains replacement**
  The project's own guides and the documentation site explain how plugin authors decide unchanged, update or replace using what they are told about their dependencies. They also show how plans display replacements and their reasons.

## Constraints

- **Built to the design.** The change follows the design document `replacement-and-dependency-changes.md` in the `design` source: the unchanged/update/replace answer, what a resource is told about its dependencies, deciding everything before acting, and the destroy-then-create order. A disagreement with the design goes to the user rather than being designed around.
- **The plugin decides.** Whether a resource is replaced is the plugin's decision, made when it is asked whether the resource changed. xcl does not infer replacement from configuration markers or rules of its own.
- **Breaking the plugin interface is allowed.** The plugin contract and the protocol for plugins that run as separate programs may change incompatibly. No compatibility layer for the old yes/no answer is required.
- **Saved state may break.** State saved by the current version does not have to load after this change; no migration of existing saved state is required.
- **Replacement destroys first.** A replaced resource is always destroyed before it is created again; there is no create-before-destroy.
- **Tests follow the repository rules.** testify `require`, no table-driven tests, positive and negative cases in separate test functions, Mockery for mocks.

## Acceptance Criteria

- [ ] **A plugin's replace answer becomes a replacement**
  When a plugin answers "replace" for a changed resource, the plan lists that resource as a replacement. After apply, the old resource is gone and a new one exists with the new configuration.
- [ ] **A plugin's update answer stays an in-place update**
  When a plugin answers "update", the plan lists the resource as an update, and apply updates it without destroying it.
- [ ] **Dependents are told about replaced and updated dependencies**
  A test plugin that records what it is told sees, for a resource referencing a replaced dependency and an updated dependency, exactly those two, each with its outcome. It is not told about a dependency that is unchanged.
- [ ] **A dependent may stay unchanged**
  When a dependency is replaced and the dependent's plugin answers "unchanged", the dependent is neither updated nor replaced.
- [ ] **Destroys happen before creates, dependents first**
  With a network replaced and a container on it replaced, the events reported during the apply show the container destroyed, then the network destroyed, then the network created, then the container created.
- [ ] **A failing decision changes nothing**
  When a plugin's change decision fails for one resource, the apply fails and no resource is created, updated or destroyed.
- [ ] **Plans name the dependency behind a replacement**
  The plan for the address-range change configuration shows the network as replaced, and the container as replaced naming the network as the reason.
- [ ] **A failed replacement is retried**
  When creating a replaced resource fails, the next plan lists that resource as a replacement again.
- [ ] **External and built-in plugins behave the same**
  The same change, applied once through a plugin built into the program and once through the same plugin run as a separate program, produces the same plan and the same apply outcome.
- [ ] **The plugin example's address-range change rebuilds the network**
  In the plugin example, applying the main configuration and then the address-range change configuration leaves Docker with the network on the new address range, a new container attached to it, and a template rendered with the new container's address.
- [ ] **The main example configuration applies alone**
  Applying the plugin example's main configuration on its own succeeds and creates the network, container and template, and the example's existing tests pass.
- [ ] **All repository plugins and tests pass**
  The full test suite, every example's tests and the external test plugins build and pass with the new change decisions.
- [ ] **The documentation shows replacement**
  The documentation site has a section, reachable from the guides, explaining "unchanged, update or replace" for plugin authors. The plugin example and diff pages show a plan with a replacement and its reason. The site builds.

## Technical Approach

- **Reuse the existing replacement path.** Resources saved as failed are already replaced, by destroying and then creating them. A plugin-decided replacement should travel the same road rather than a second mechanism.
- **Plans and applies share one decision pass.** A plan is the decision pass run on its own, so a plan never disagrees with what the apply then does.
- **Keep the example's second configuration apart.** Keep the address-range change configuration in its own directory beside the main one.
- **Risk: every plugin changes at once.** The contract change touches every in-repo plugin and the protocol for out-of-process plugins in one go. The planner should sequence it so the repository keeps building.
- **Risk: decisions before reads.** Deciding everything before acting means a dependent decides without its dependency's new computed values. It sees only that the dependency will change, and those values show as unknown in plans.

## Success Metrics

- After the address-range change configuration is applied in the plugin example, the Docker network's address range matches the configuration, and the next plan reports no changes: no drift between state and reality.
- For each plugin in the repository, every setting it cannot change in place has a test showing it answers "replace".
- The plan shown before an apply lists exactly the resources the apply then destroys, creates or updates, with nothing extra and nothing missing.

## Non-Goals

- **Replacing after a failed update.** A plugin cannot turn a failed in-place update into a replacement; a failed update fails as it does today.
- **Cascading deletes.** Removing a resource from the configuration does not change how its dependents are decided, because a removed resource can't still be referenced by a configured one.
- **Plugin registration returning errors.** Whether a plugin's own type and provider registration should stop returning errors is a separate question, outside this change.
- **The editor extension.** No new configuration syntax is introduced, so the editor extension needs no change.
