# Feature: 20261014052450-0b131707-ci-release-automation

## Overview

Releasing xcl and its language packages is manual today, and they're tied together: every language package shares the engine's version number, so a fix to one language means a new release of every language. An engine change that breaks a language package is only discovered at release time, after the release has already been made. This change makes each pull request declare how big a change it is, and releases happen automatically when it merges. An engine pull request can't merge while any language package fails against it, unless a maintainer deliberately marks the breakage. Each language package gets its own version and release, and picks up new engine releases through its own automatically verified update. Maintainers get a hands-off, documented release process, and fixes reach each language without forcing releases elsewhere.

## Requirements

- [ ] **Every PR declares its release size**
  Every pull request on xcl and on each language package carries exactly one release label: `major`, `minor`, `patch` or `no-release`. A pull request with no release label, or with more than one, can't be merged.
- [ ] **Merging releases automatically**
  When a pull request with `major`, `minor` or `patch` merges, the repository is tagged with the next version for that label and the release runs, with no manual step.
- [ ] **No-release merges don't release**
  When a pull request labelled `no-release` merges, no tag is created and nothing is published.
- [ ] **Major before 1.0**
  While a repository is below 1.0, a `major` label releases 1.0.0.
- [ ] **Engine PRs are checked against every language**
  An xcl pull request runs xcl's own checks and each language package's full test suite against the pull request's own code, and shows each result on the pull request.
- [ ] **Failing language blocks the merge**
  An xcl pull request can't be merged while any language package's check fails, unless it carries the override label.
- [ ] **Override for intentional breaks**
  A maintainer can add an override label (its name is left to the plan) to an xcl pull request so it can merge while a language package's check fails. Only people with permission to label pull requests can apply it, and the pull request shows which checks failed.
- [ ] **Language packages version independently**
  Each language package has its own version number and release history, separate from the engine's.
- [ ] **Language-only changes release only that language**
  Merging a release-labelled pull request on a language package releases only that package. The engine and other language packages don't release.
- [ ] **Each language release names its engine**
  Each language package release bundles one specific engine release, runs only on that engine, and states in its release notes which engine it bundles.
- [ ] **Engine releases propagate by verified update**
  When the engine releases, each language package automatically gets a pull request that moves it to the new engine. That pull request runs the package's full checks.
- [ ] **Green updates release themselves**
  An engine-update pull request whose checks pass merges and releases without a maintainer. Its release size matches the engine's: an engine patch gives a package patch, an engine minor gives a package minor, and an engine major gives a package major (1.0.0 while the package is below 1.0).
- [ ] **Red updates wait**
  An engine-update pull request whose checks fail stays open and unreleased until a maintainer fixes it.
- [ ] **Release notes**
  Each automatic release has release notes built from the changes merged since the previous release.
- [ ] **Process documented**
  xcl's README describes the whole process: the labels, the cross-language checks, the override, automatic releases and how engine releases reach each language package. Each language package's README has a short section on its own labels and engine pin, linking to xcl's.

## Constraints

- The automation runs on GitHub: GitHub Actions for checks and releases, and GitHub's merge protection to enforce required checks and labels.
- Engine releases must stay signed with the jumppad-labs release key, and the Python package must keep publishing to PyPI under its existing name for the platforms it supports today.
- A language package's first independently versioned release must be higher than every version it already has on its package registry, since registries refuse to reuse a version.

## Acceptance Criteria

- [ ] **Missing or double label blocks merge**
  A pull request on xcl or xcl-python with no release label shows a failing required check and can't be merged. Adding one label turns the check green. Adding a second release label turns it red again.
- [ ] **Patch, minor and major tag the right version**
  From a latest tag of `v0.7.0`, merging a `patch` PR creates `v0.7.1`, a `minor` PR creates `v0.8.0`, and a `major` PR creates `v1.0.0`. Each tag's release runs with no manual step.
- [ ] **No-release merges are silent**
  Merging a `no-release` PR creates no new tag, no GitHub release and no package upload.
- [ ] **Language results appear on the engine PR**
  An xcl PR shows a separate check for the Python suite, run against the PR's head commit, alongside xcl's own checks.
- [ ] **Python failure blocks an engine PR**
  An xcl PR that makes the Python suite fail can't be merged, and the failing Python check is shown.
- [ ] **Override lets an intentional break through**
  The same failing xcl PR can be merged once a maintainer adds the override label. A contributor without labelling permission can't apply it.
- [ ] **Python fix releases only Python**
  Merging a `patch` PR on xcl-python publishes a new Python package version, one patch above the last, bundling the same engine as before. No xcl tag or release is created.
- [ ] **Python reports its pinned engine**
  An installed Python package reports the engine version it bundles. It refuses to run against a different engine version, and its release notes name the bundled engine.
- [ ] **Engine release opens a verified update**
  After an xcl release, xcl-python has an open pull request that moves its engine pin to the new tag, with Python's full checks running on it.
- [ ] **Green update releases Python**
  For an engine `patch` release, the update PR in xcl-python merges itself once its checks pass, and a Python package one patch above the last is published, bundling the new engine. An engine `minor` gives a Python minor, and an engine `major` gives a Python major.
- [ ] **Red update waits**
  When the update PR's checks fail, it stays open and unmerged, and no Python package is published.
- [ ] **Release notes list merged changes**
  Each automatic GitHub release lists the pull requests merged since the previous release.
- [ ] **Signatures and publishing still verify**
  The engine release's checksums file verifies against the jumppad-labs release key. The Python package installs from PyPI under its existing name on every platform it supports today.
- [ ] **Process is documented**
  xcl's README has a section describing the labels, the cross-language checks, the override, automatic releases and engine propagation. xcl-python's README has a section on its labels and engine pin that links to it.

## Technical Approach

- Prefer the simplest process that works; favour built-in platform features over custom tooling.
- Cross-language checks: each language package publishes a reusable workflow that takes an xcl ref; xcl's pull request workflow calls each with the PR's head commit, so results show as ordinary checks on the xcl PR. Adding a language means adding one call.
- Engine pin: each language package's existing pinned xcl ref (Python's `xcl-ref.txt`) becomes the single source of which engine it tests against and bundles; the runtime engine check compares against that pin rather than the package's own version.
- Engine propagation: the xcl release triggers each language repo, as the current release dispatch already does, but to open the pin-update PR instead of publishing directly.
- Release triggering: tags pushed by the default Actions token don't start other workflows; consider a GitHub App (or similar) token for the tagging step, or having it call the release workflow directly.
- Release notes from the PRs merged since the previous tag; the plan may decide whether the existing changelog records feed them.
- Reuse the existing build and publish pipeline (signed `xcl-core` build, wheel matrix, parity runs at release, PyPI trusted publishing); this work changes what starts a release and which version it gets.
- Risk (migration): Python moves from lockstep to its own version line; choosing its starting version is part of the rollout (see Constraints).
- Risk (ordering): roll out the reusable Python workflow on xcl-python `main` before making it a required check on xcl.

## Success Metrics

- Proven on real work: the parked Python plain-dataclasses spec ships through this process end to end — its xcl PR merges via the override label, Python's engine-update PR goes red until the Python fix lands, then Python releases on its own — with no manual tag or publish.
- No manual tags: after rollout, every xcl and xcl-python release comes from a merged, labelled PR; no tags are pushed by hand.
- No surprise breakage at release: no xcl release is followed by a Python failure that wasn't already visible on the xcl PR, as a green check or an explicit override.
- Language fixes stay local: a Python-only fix reaches PyPI without any xcl release.
- Engine fixes reach Python without hands: an engine `patch` release produces a published Python package with no maintainer action when the update PR is green.

## Non-Goals

- Other repos: plugin repos (docker, template, test), xcl-website and xcl-vscode do not adopt the labels or cross-repo checks in this work.
- New languages: Python is currently the only language package; the process is built to take more, but none are added here.
- How artefacts are built: engine compilation, the wheel platform matrix and the in-process shared library build are unchanged.
- The Python API: that is the parked plain-dataclasses spec, the first real test of this process, not part of it.
- Same-branch-name coordination: coordinated breaking changes go through the override label, not automatic branch matching.
