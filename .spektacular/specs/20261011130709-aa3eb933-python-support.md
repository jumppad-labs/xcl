# Feature: 20261011130709-aa3eb933-python-support

## Overview

Python developers can't use XCL today: it only exists as a Go library. This spec brings XCL to Python by running the same engine that Go programs use, rather than rewriting it. That way a Python program reads, checks and applies configuration exactly as a Go program would, uses the same plugins, and can add its own functions to configuration. It serves people building command-line and Jumppad-style tools in Python and teams running asynchronous Python services. It's the first step in making XCL a language with more than one implementation, and the API it settles shapes how XCL's documentation is reorganised to cover more than one implementation.

## Requirements

- [ ] **Install with pip, no toolchain**
  Users can install XCL for Python from PyPI as the distribution `xcl-lang` (imported as `xcl`) with `pip install xcl-lang` on Linux (x86-64 and arm64, glibc and musl), macOS (x86-64 and arm64) and Windows (x86-64 and arm64), without Go or a C compiler.
- [ ] **Python 3.10 and later**
  The package works on CPython 3.10 through the latest stable CPython release at the time of each XCL release.
- [x] **Entity types as Python classes**
  Developers can define an entity type as a Python class and register it, with the type and an optional subtype becoming the block's labels and address, as in Go.
- [x] **Python types map to configuration**
  Optional fields, defaults, sensitive and computed fields, nested blocks, lists of blocks and named blocks collected by name are all expressed with Python type annotations, and configuration is checked against them as it is for Go types.
- [x] **Python functions callable from configuration**
  Developers can register a Python function, and configuration can call it. The result is filled in exactly like a built-in function's.
- [x] **Go plugins usable from Python**
  A Python program can use Go-compiled plugins from a local path, a plugin directory or the GitHub registry, with release signatures verified as they are for Go programs.
- [x] **Every operation available**
  A Python program can validate, diff, apply, load and destroy configuration, with the same results a Go program gets for the same configuration, plugins and state.
- [x] **Variables passed in**
  A Python program can supply variable values when it creates a configuration.
- [x] **Entities read back as Python objects**
  A Python program can find entities by address, by type, exactly one of a type, and all of a type, and gets instances of its registered classes. Entities of types it hasn't registered, such as a Go plugin's types, are readable generically.
- [x] **Outputs and diffs readable**
  A Python program can read a configuration's outputs, and a diff's changes, as Python values.
- [x] **State location and custom stores**
  A Python program can keep state in a directory, or in its own store written in Python, and can have sensitive values encrypted in state.
- [x] **Events delivered to Python**
  A Python program can receive the engine's events through a handler, with the same event data levels and masking a Go program has.
- [x] **Errors as Python exceptions**
  Failures surface as Python exceptions, one class for each kind of error, carrying the message, the details and any configuration positions.
- [x] **Synchronous API**
  A synchronous API runs each operation to completion before returning, and other Python threads keep running while it works.
- [x] **Asynchronous API**
  An asyncio API offers every operation as an awaitable that never blocks the event loop. Python functions, event handlers and custom state stores may be async under it.
- [x] **Cancellation stops the work**
  Cancelling an awaited operation stops it in the engine, rather than leaving it running in the background.
- [x] **Safe across fork**
  Using a configuration in a process forked after XCL was used raises a clear error that explains the safe alternatives. A process that imports XCL but hasn't used it before forking is unaffected.
- [x] **Engine version checked**
  The package refuses to run against an engine whose version doesn't match its own, with an error saying so.
- [ ] **Releases kept in step**
  Every XCL release publishes a Python package with the same version, carrying the engine built from that release.
- [x] **Package documentation**
  The Python package ships a README covering install and getting started (synchronous first, then asynchronous), and every public class and function has a docstring.

## Constraints

- The work is built to the settled design in the `design` source at `libxcl.md`. That design covers the engine compiled once as a shared library, one protobuf message API through one C function, schema v1, and the Python packaging and loading.
- Python functions and named blocks collected by name behave exactly as the language-surface spec (`20261011095738-fad05e41-language-surface`) defines them for Go, and this spec is implemented after that one.

## Acceptance Criteria

- [ ] **Clean install on every platform**
  On a fresh machine for each of the eight platforms, with no Go or C compiler, `pip install xcl-lang` succeeds and `python -c "import xcl; xcl.Config().close()"` runs without error.
- [ ] **Supported Python versions**
  The test suite passes on CPython 3.10, 3.11, 3.12, 3.13 and the latest stable release.
- [x] **Registered class decodes config**
  With a class registered as `app`, `app "web" { image = "nginx" }` validates and applies, and finding `app.web` returns an instance of that class with `image == "nginx"`. A class registered as `database` with subtype `postgres` decodes `database "postgres" "main" { … }` and is found at `database.postgres.main`.
- [x] **Annotations enforced**
  For a class with a required field, an optional field with a default, a sensitive field, a computed field, a single nested block, a list of `volume` blocks and a map of named `listener` blocks:
  - leaving out the required field fails validation at the block's position;
  - leaving out the optional field gives the default;
  - the sensitive value is masked in events and state;
  - the computed field can't be set in config;
  - the nested block is decoded into its class;
  - two `volume` blocks give a list of two items in order;
  - two `listener "…"` blocks give a dict keyed by their names.
- [x] **Python function called**
  With `slugify` registered, `name = slugify("My App")` applies, and the entity holds `"my-app"`.
- [x] **Async function called**
  Under the asyncio API, a registered `async def` function is awaited and its result filled in.
- [x] **Go plugin from path and registry**
  A Python program applies config whose entities are handled by the Docker example plugin, loaded from a local path, from a plugin directory and from the GitHub registry. A tampered release asset is refused, with a signature error.
- [x] **Same results as Go**
  For a shared set of fixture configurations, the Python and Go programs produce the same validation errors, the same diff, the same entities and outputs after apply, and the same state file contents. A load in a new process reads back the same entities in both, and a destroy removes every entity and empties the state in both.
- [x] **Variables supplied**
  Passing `region = "us"` when creating the configuration makes an entity that uses `variable.region` hold `"us"`.
- [x] **Unregistered types readable**
  Entities of a Go plugin's type, with no Python class registered, are returned with their address and attributes readable by name.
- [x] **Outputs and diff**
  After apply, outputs are returned as a dict of Python values. A diff after changing one attribute reports that attribute's old and new values.
- [x] **State directory**
  With a state directory set, an apply writes state there, and a load in a new process reads it back.
- [x] **Custom state store**
  A Python object implementing the store methods receives the state on apply, and a later load in a new process reads it back. With state encryption enabled, sensitive values in what the store receives are encrypted.
- [x] **Events received**
  An event handler receives an event for each entity's start and finish during an apply, and with event data on, sensitive values in event data are redacted.
- [x] **Typed exceptions**
  A missing address raises the not-found exception, asking for exactly one entity of a type when several exist raises the not-unique exception, and invalid config raises the config exception, which lists each problem with its file and line.
- [x] **Sync doesn't stall threads**
  While a synchronous apply runs a slow plugin operation, a second Python thread keeps making progress.
- [x] **Async doesn't block the loop**
  While an asyncio apply runs a slow plugin operation, other coroutines on the same event loop keep running.
- [x] **Cancellation**
  Cancelling an asyncio apply mid-way makes it end promptly with a cancellation error, and a test plugin records no operations started after the cancellation.
- [x] **Fork protection**
  Using a configuration in a child forked after the parent used XCL raises the fork error, which names the `spawn` start method and creating the configuration after the fork. A child forked from a parent that only imported XCL works normally.
- [x] **Version mismatch refused**
  Running the package against an engine of a different version raises an error naming both versions.
- [ ] **Release publishes matching package**
  Tagging an XCL release publishes the same version to PyPI, with a wheel for each of the eight platforms, and that version's engine reports the tag.
- [ ] **Docs present**
  The PyPI project page shows the README with install, a synchronous getting started and an asynchronous section. Every public name in the package has a docstring.

## Technical Approach

- Build the synchronous and asyncio APIs as two faces over the single poll loop the design describes, rather than two implementations.
- Carry Python functions through the poll loop as tasks the host completes with the result, following the pattern the design sketches for host-language functions. The core builds the function from a signature the Python side declares.
- The poll loop carries function, event and state tasks; the design's provider registration and provider tasks aren't needed.
- Connect asyncio cancellation to the context-taking operation methods the design adds to the root module, so a cancelled task cancels the engine's work.

## Success Metrics

- A Python developer goes from `pip install xcl-lang` to a working apply against a Go plugin by following the package README alone.
- Every operation and lookup in the Go API has a Python equivalent in both the synchronous and asyncio APIs, checked against a parity list at release.
- The Go–Python parity fixtures pass on every release, on every published platform.
- An async web service using the asyncio API keeps serving other requests during a long apply.

## Non-Goals

- Python providers registered in process: Python programs use Go-compiled plugins and config-only types only.
- Python plugins run out of process, the Python plugin SDK and plugin protocol v2. These are a later spec.
- Distributing Python plugins through the GitHub registry.
- Node and TypeScript support.
- Python documentation on xcl.dev. It's written later by the epic's docs specs, once this API is settled.
