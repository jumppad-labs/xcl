# Feature: 20260921093100-query-api-v2

## Overview

Reaching into a parsed configuration already works, but it is more awkward than it needs
to be: every lookup begins by building a helper object that is used once and thrown away,
a question that cannot be answered comes back looking like a legitimate answer of "none",
and a mismatched request can return a blank result without complaint. This work rebuilds
that experience around the configuration itself — you ask the configuration directly for a
single item by its address, for everything of a given kind, or for the one item you expect
there to be exactly one of — taking advantage of generic methods in Go 1.27 so a lookup
reads as one call instead of two, while keeping a portable equivalent for consumers who
are not yet on a new enough toolchain. It also brings the values a configuration publishes
for its consumers into that same lookup, so a caller no longer has to know they are held
differently in order to ask for one by name.

Developers building on this library get a shorter and more obvious way to reach a value,
and get their mistakes reported at the point they are made rather than surfacing later as
puzzling empty or blank results.

## Requirements

### Asking a configuration for what you want

- [x] **Lookup by address in a single call**
  Developers can retrieve one declared item by its address, as their own Go type, in a
  single call on the parsed configuration — without first constructing a throwaway helper
  bound to that type.

- [x] **Lookup of every item of a kind**
  Developers can retrieve all declared items matching a kind, as their own Go type, by
  supplying the same leading address segments, in the same order, that those items'
  addresses use.

- [x] **Lookup of the single expected item**
  Developers can ask for the one item they expect a configuration to declare exactly one
  of, and receive it directly rather than a collection they must index into. Finding none
  and finding more than one are each reported as distinct, recognisable outcomes, and the
  more-than-one outcome reports how many were found.

- [x] **Lookup of everything of a Go type, without naming it in a string**
  Where a Go type has been registered with the system, developers can retrieve every
  declared item of that type without restating its name as a string, with the addressing
  derived from the registration.

- [x] **Enumeration of everything declared**
  Developers can enumerate every item a configuration declares — of every kind, including
  those that are not resources — without naming a type.

- [x] **Converting an enumerated item to a Go type**
  Developers can convert an item obtained from an untyped enumeration into their own Go
  type in one call, without first extracting its metadata by hand.

- [x] **Consecutive lookups of different types cost nothing extra**
  Developers can perform consecutive lookups of different Go types against the same
  parsed configuration without per-type setup between them.

### Published values

- [x] **Published values reachable by address**
  Developers can retrieve a single value a configuration publishes for its consumers using
  the same address-based lookup used for everything else. Retrieving one by address
  requires no knowledge of how such values are stored.

- [x] **Published values return the value, not the container**
  A lookup of a published value yields the resolved value itself, converted to the type the
  caller asked for, rather than the declaration that produced it.

- [x] **Published values require a full address**
  A lookup of a published value must be given its complete address, including the module it
  belongs to where it belongs to one. A bare name is not an address and must not be inferred.

- [x] **Every published value enumerable together**
  Developers can obtain every published value a configuration produces, keyed by address, in
  one call.

### Honest answers

- [x] **An empty result and an unanswerable question are distinguishable**
  A query that is well-formed but matches nothing returns an empty result and no error. A
  query that cannot be answered returns an error. These two outcomes must never be
  represented the same way.

- [x] **Each failure reason is independently recognisable**
  Callers can determine programmatically which of the failure reasons occurred — the address
  matched nothing, the named kind is not a kind, the query spans more than one Go type, the
  Go type was never registered, the item is not of the requested type, the requested type is
  not addressable at all, or more than one item matched a query expecting one — and can
  recover the detail behind each.

- [x] **A mismatched type is refused, not silently converted**
  Where the system knows what an item's type should be, a request to convert it to a
  different Go type is refused with an error. Conversion must never yield a partially
  populated or entirely zero value in place of an error.

- [x] **Nested blocks report that they are not addressable**
  A request that treats a block nested inside another declaration as though it were
  independently addressable is refused with an error naming that it is reached through the
  declaration that contains it. It must not be answered with an empty result, which would
  read as "you declared none".

- [x] **Unregistered plugin-provided types report the form that does work**
  Where a Go type cannot be matched because the type lives inside a plugin and only a schema
  is available, the failure names the query form that does work instead.

- [x] **One not-found concept for configuration lookups**
  A failure to find a declared item reports as a single recognisable not-found condition
  across the lookup surface, irrespective of which internal component reported it, and stays
  distinct from the unrelated not-found condition that means real infrastructure is missing.

### The data model behind the lookups

- [x] **Kind and variety recorded separately for every declaration**
  Every declared item without exception reports the kind of stanza it is and its specific
  variety independently, and neither is reported in place of the other. Items with a single
  label report an empty variety.

- [x] **Addresses carry the variety**
  The system must accept and produce addresses in which the variety is its own segment, so
  that an address and a positional kind query agree on the same grammar.

- [x] **The two stanza forms stay distinct**
  A declaration written with a leading kind keyword and a declaration written with the
  variety as the leading keyword are treated as different types with different addresses.
  Neither is rewritten into the other, and a Go type is registered under one form only.

- [x] **Both stanza forms can be declared**
  Configuration authors can declare a top-level item using its variety as the leading
  keyword with a single label, and the system accepts it as a valid declaration alongside
  the existing kind-led form. This exists to make the addressing model's treatment of the
  two forms observable, and is a facilitating change rather than part of the referenced
  API design.

### Reaching developers on older toolchains

- [x] **Portable equivalent for the supported floor**
  Every lookup available as a method is also available in a form that compiles and behaves
  identically on the project's declared minimum Go version, so that consumers who cannot
  adopt the newer toolchain lose no capability.

- [x] **The two forms cannot drift**
  The two spellings must produce identical behaviour for identical inputs, and this must be
  verified rather than assumed.

- [x] **The floor build is proven continuously**
  The build on the minimum supported Go version is verified automatically on every change,
  because no contributor exercises that path locally and a break in it is otherwise silent.

### Migration of existing consumers

- [x] **The superseded query helper is gone**
  The previous construct-then-call query helper and its methods are removed, not deprecated
  alongside the new surface.

- [x] **Bundled examples and tests use the new surface**
  Every example and test in this repository uses the new surface, written in the form that
  compiles on the minimum supported Go version so that what a reader copies works for them.

- [x] **Enumeration and counting named for what they hold**
  The operations that enumerate and count everything a configuration declares are named for
  the fact that they cover every kind of declaration, with the previous names retained as
  deprecated aliases. The specific names are fixed by the referenced design document.

- [x] **Library documentation covers the new surface**
  The library's own documentation replaces its description of the superseded query helper
  with the new surface, and additionally documents retrieving published values, which it
  does not cover today.

- [x] **The documentation site carries no superseded examples**
  Every page on the documentation site that demonstrates or names the superseded query
  helper is updated to the new surface, including the landing page's headline example and
  its accompanying feature description. Site examples use the form that compiles on the
  minimum supported Go version.

## Constraints

- The `querier-api-v2` design document is binding. The solution must conform to the API
  surface, vocabulary, error taxonomy and delivery mechanism it specifies. Where this spec
  and the design document disagree on *how*, the design document governs; where they
  disagree on *what must be true*, this spec's requirements and acceptance criteria govern.
- The project's minimum supported Go version must remain 1.25.0. Raising the declared floor
  to reach newer language features is not available as an option, because consumers cannot
  be compelled onto a newer toolchain.
- Generic methods are unavailable below Go 1.27. This is a language-level fact, not a design
  choice.
- Capability must not be gated on toolchain version. A consumer on the minimum supported
  version must be able to do everything a consumer on the newest toolchain can do; the two
  forms may differ in spelling but not in what they make possible.
- Error handling must follow the convention already established in this codebase — sentinel
  values matched by identity, each wrapped by a type carrying the specific detail — rather
  than introducing a second convention alongside it.
- The "entity" vocabulary is fixed by the existing plugin boundary. The type-and-subtype
  taxonomy and the term itself are already in the plugin wire format, so the naming here
  must match it rather than introduce a third vocabulary.
- Plugin-provided types exist host-side only as schemas. There is no Go type to reflect
  against for a type registered inside a plugin, so any mechanism that derives addressing
  from a Go type cannot serve them and must say so.

## Acceptance Criteria

### Asking a configuration for what you want

- [x] **An address lookup returns a typed item from one call**
  Given a configuration declaring an item, an address lookup for that address, asking for
  the matching Go type, returns a populated value of that type and no error, in a single
  call expression with no intermediate value constructed first.

- [x] **Address lookups tolerate the address forms already in use**
  An address lookup succeeds when given a module-relative address, a non-normalised
  address, and an address carrying a trailing attribute suffix such as one taken verbatim
  from a stored reference between items — all three resolving to the same item.

- [x] **A kind lookup returns every match and only matches**
  Given a configuration declaring three items of one variety and two of another, a kind
  lookup naming the kind and the first variety returns exactly three values of the
  requested Go type, and a kind lookup naming the kind and a variety with nothing declared
  returns an empty result and no error.

- [x] **A variety name alone matches nothing**
  A kind lookup given only a variety name, with no kind preceding it, does not return
  items of that variety; it fails rather than matching positionally in the wrong place.

- [x] **The single-expected lookup discriminates all three outcomes**
  Against a configuration declaring exactly one matching item the single-expected lookup
  returns that item and no error; against one declaring none it returns an error
  recognisable as not-found; against one declaring two or more it returns an error whose
  reported detail includes the number found.

- [x] **A registered Go type is queryable without a string**
  For a Go type registered with the system, a lookup that names only the Go type — passing
  no address segments — returns every declared item of that type, matching what the
  equivalent kind lookup returns for the same configuration.

- [x] **Enumeration covers every kind of declaration**
  Enumerating everything a configuration declares yields entries for resource-kind items,
  variables, published values and modules alike, and the count of entries matches the
  number of declarations in the configuration.

- [x] **An enumerated item converts in one call**
  An item taken from the untyped enumeration converts to its corresponding Go type in a
  single call that requires no prior metadata extraction, returning a value equal to the
  one an address lookup for the same item returns.

- [x] **Different types query back to back**
  Two consecutive lookups of two different Go types against the same parsed configuration
  both succeed, with no setup call between them.

### Published values

- [x] **A published value is retrieved by address**
  Given a configuration that publishes a value, an address lookup for that value's address
  returns it, using the same call used to retrieve any other declared item.

- [x] **The value is returned, not its declaration**
  An address lookup for a published value, asking for the type of the value itself,
  returns that value converted to the requested type — not the declaration that produced
  it, and not a zero value.

- [x] **A module's published value resolves by its full address**
  A published value declared inside a module is retrieved by its complete address
  including the module, and a lookup of the bare name alone fails rather than resolving.

- [x] **All published values are obtainable together**
  A single call returns every value the configuration publishes, keyed by address, with
  one entry per published declaration.

### Honest answers

- [x] **Empty and unanswerable are never the same response**
  A well-formed query matching nothing returns an empty result with a nil error, while a
  query naming something that is not a kind returns a non-nil error — the two are
  distinguishable without inspecting the result contents.

- [x] **Each failure reason is separately identifiable**
  Each of the failure conditions — address matched nothing, named kind is not a kind, the
  query spans more than one Go type, the Go type was never registered, the item is not of
  the requested type, the requested type is not addressable, and more than one matched a
  single-expected query — is distinguishable programmatically from every other, and the
  specific detail behind each is retrievable by the caller.

- [x] **The kind axis and published values fail alike**
  A kind lookup naming only the kind that spans multiple Go types, and a kind lookup naming
  published values, both return the same not-typeable failure, and the published-values
  case names the dedicated call that does return them.

- [x] **A mismatched conversion errors instead of returning blanks**
  Converting a declared item to a Go type that does not correspond to it returns a
  type-mismatch error and no value. Repeating this across a set of items of differing
  types produces an error for every mismatch and never a value whose fields are unset.

- [x] **A nested block query is refused, not answered emptily**
  A kind lookup naming a block that exists only nested inside another declaration returns a
  not-an-entity error rather than an empty result, and a Go-type lookup for that same
  nested block's type returns the same error. The error's message names access through the
  containing declaration.

- [x] **A plugin-provided type is told which query works**
  A Go-type lookup for a type that exists only inside a plugin returns a not-registered
  error whose message names the kind-lookup form as the working alternative.

- [x] **Not-found is one condition across the lookup surface**
  A not-found outcome originating from stored state and a not-found outcome originating
  from the lookup surface are both recognisable as the same not-found condition, while the
  unrelated not-found condition meaning real infrastructure is absent remains
  distinguishable from both.

### The data model behind the lookups

- [x] **Every declaration reports both axes**
  For a configuration containing a resource-kind declaration with a variety, a variable, a
  published value and a module, every one exposes a kind, and the resource-kind declaration
  additionally exposes its variety while the other three expose an empty variety. No
  declaration reports its variety in place of its kind.

- [x] **Kind-axis queries no longer return silent empties**
  A kind lookup naming the resource kind returns the not-typeable error rather than the
  empty result it returns today.

- [x] **Addresses round-trip with the variety segment**
  An address containing a variety segment parses into its parts and formats back to the
  identical string, and an address produced for a declaration is accepted by an address
  lookup for that same declaration.

- [x] **The bare stanza form is accepted**
  A configuration declaring a top-level item with its variety as the leading keyword and a
  single label parses without error, and the resulting declaration reports that keyword as
  its kind and an empty variety.

- [x] **The two stanza forms address differently**
  A configuration declaring one item with a leading kind keyword and another of the same
  variety with the variety as the leading keyword yields two declarations with different
  addresses, each returned by its own kind lookup and neither returned by the other's.

### Reaching developers on older toolchains

- [x] **The library builds and its tests pass on the minimum supported version**
  Building the module and running its tests with the toolchain pinned to the project's
  declared minimum Go version succeeds, with the portable form of every lookup available
  and exercised.

- [x] **Both forms produce identical results**
  For every lookup, a test asserts that the method form and the portable form return
  equal values and equal errors for identical inputs, and this assertion runs on a
  toolchain where both forms are available.

- [x] **The minimum-version build runs unattended on every change**
  Continuous integration includes a job that builds the module against the pinned minimum
  Go version, and that job runs on every change rather than on demand.

### Migration of existing consumers

- [x] **The superseded helper is absent from the public surface**
  Building code that constructs the previous query helper fails to compile against the new
  version, and no reference to it remains anywhere in the repository.

- [x] **Every bundled example and test uses the new surface**
  The repository's examples and tests contain no use of the superseded helper, all compile
  under the pinned minimum Go version, and every example runs to completion producing its
  expected output.

- [x] **Enumeration and counting answer to both names**
  The enumeration and count operations are available under their new names, and calls
  written against their previous names still compile and return identical results while
  being marked deprecated.

- [x] **Library documentation shows the new surface and published values**
  The library's own documentation contains no description of the superseded helper, shows
  the new surface in its place, and contains a worked example of retrieving a published
  value where it previously had none.

- [ ] **No documentation-site page shows the superseded helper**
  Searching the documentation site's sources for the superseded helper's name returns no
  matches, the landing page's headline example and its accompanying feature description
  both show the new surface, and every code sample on the site compiles under the pinned
  minimum Go version.

## Technical Approach

- No technical direction has been decided beyond what the requirements and constraints
  already capture; the worked design is settled elsewhere and the remaining implementation
  detail is left for the plan workflow to propose.
- One area of genuine uncertainty worth flagging for planning: there is no established
  mechanism for verifying that code samples in the documentation site actually compile. The
  acceptance criteria require it, so the plan will need to propose how — extracting samples
  into buildable files, or some equivalent — rather than assuming a mechanism exists.

## Success Metrics

- Every one of the existing lookup call sites in the repository — 8 in examples, 7 in tests
  — reduces from a construct-then-call pair to a single call expression, with none
  requiring more code after migration than before.
- Zero query forms answer an unanswerable question with an empty result: each of the seven
  identified failure conditions is covered by a test asserting its specific error,
  including the kind-axis query that returns silently empty today.
- Zero paths return a partially populated value in place of an error, evidenced by mismatch
  tests covering conversion of each registered type to a non-corresponding type.
- Retrieving a published value requires no knowledge of how it is stored, evidenced by at
  least one bundled example and one documentation sample that retrieves one using an
  address alone.
- A search for the superseded query helper across the library and the documentation site
  returns zero matches.
- The minimum-supported-version build job passes on every change from merge onward, with no
  period in which it is absent or skipped.

## Non-Goals

- Exposing the dependency graph, or providing a public dependency-ordered walk over a
  configuration.
- Indexing or lookup-performance optimisation.
- Populating the per-item properties map that is allocated but never written today.
- Migrating configuration state written by the previous version; regenerating it is
  acceptable.
- A migration guide, deprecation window, or compatibility shim for consumers outside this
  repository, since the version carrying these changes is unreleased and has none.
- New documentation-site pages covering published values or error semantics. Existing pages
  move to the new surface; broadening the site's coverage is separate work.
- Correcting the library documentation's stale sections describing operations that no
  longer exist. That cleanup is unrelated to this change and is tracked separately.
- Any change to how a configuration is authored beyond accepting the additional stanza
  form. The expression language, existing stanza keywords and their meanings are unchanged;
  this work is otherwise about how a parsed configuration is consumed.
