## Overview

Passwords and other secrets declared in a configuration currently appear in plain text wherever xcl or the application prints, logs or reports them. This lets type authors declare a value sensitive, keeps it sensitive as it flows through references, interpolation and module outputs, and ensures it never appears in logs, errors or printed output, while state keeps the real value and application code gets it by explicitly unwrapping it, so it always knows it is handling a secret.

## Requirements

- [x] **Type authors can declare a field sensitive**
  A type author can declare that a field holds a sensitive value, both for types registered by the application and for types supplied by plugins.
- [x] **Sensitive values can be created by applications**
  Application code can construct a sensitive value itself, for example in tests.
- [x] **Real values are available only by explicit unwrap**
  Application code reading a sensitive field gets the real value only through an explicit unwrap; every other way of formatting or serialising it, apart from writing state, yields the protected form.
- [x] **State keeps real values**
  State stores sensitive values as their real values, so they are read back unchanged after reloading, while every other serialisation shows the protected form.
- [x] **Sensitivity follows the value through the configuration**
  A value derived from a sensitive value — referenced, interpolated into a string, or passed through a function — is itself sensitive.
- [x] **A sensitive value cannot reach a plain field in configuration**
  Assigning a sensitive value, or one derived from it, to a field not declared sensitive is rejected when the configuration is validated, with an error naming the field.
- [x] **Outputs keep sensitivity**
  An output whose value is, or contains, a sensitive value is sensitive in exactly those parts: protected for a module's caller and when read by application code.
- [x] **A sensitive value cannot reach a plain field in Go**
  Decoding, converting or looking up into a Go type whose matching field is not declared sensitive fails with a type error naming the field.
- [x] **Logs never show sensitive values**
  Sensitive values written through any logging path — xcl's own, a custom handler, plugin log details, or general string formatting — appear only as the fixed marker.
- [x] **Errors never show sensitive values**
  Error messages produced by xcl show sensitive values only as the fixed marker.
- [x] **Printed and encoded output redacts by default**
  Configuration text and the resource printers show sensitive values as the fixed marker unless the developer explicitly asks to reveal them.
- [x] **Bundled examples stop printing secrets**
  The examples shipped with xcl no longer print any password or other secret in clear.
- [x] **Plugin authors are told what unwrapping gives up**
  The documentation for plugin authors explains that a value, once explicitly unwrapped, is no longer protected and must not be logged or otherwise emitted.
- [x] **Sensitive values are documented**
  The library's documentation and the documentation site describe declaring sensitive fields, unwrapping them in application code, the errors raised when a sensitive value meets a plain field, and that the application's own serialisation and templates show the fixed marker unless the value is unwrapped.

## Constraints

- Sensitivity must be declared with a sensitive Go type, `types.Sensitive[T]`, on the field — not with a struct-tag option — so the value protects itself wherever it is formatted or serialised, including in loggers xcl does not own.
- Application code must get real values in memory: lookups, listing and decoding return sensitive values wrapped, never redacted or masked.
- There must be no option to unwrap sensitive values automatically on decode, conversion or lookup; reaching a plain Go type requires an explicit unwrap.
- If parse or validation diagnostics ever render evaluated values, sensitive values in them must be redacted.

## Acceptance Criteria

- [x] **Sensitive field on an application type**
  A type registered by the application with a field declared sensitive is configured and applied, and after reloading from state the real value is available by explicit unwrap.
- [x] **Sensitive field on a plugin type**
  The same holds for a type supplied by a plugin with a field declared sensitive.
- [x] **Application-constructed sensitive value**
  Application code can construct a sensitive value from a plain value; unwrapping it returns the original value, and formatting it shows the fixed marker.
- [x] **Protected form everywhere but unwrap**
  For a sensitive value, string formatting (all verbs), structured logging, JSON and text marshalling each produce the fixed marker, never the real value; the explicit unwrap returns the real value.
- [x] **State round-trips the real value**
  After applying a configuration with a known sensitive value, a new configuration loading that state reads back the real value by explicit unwrap, while events, logs and printed output for the same entity show only the fixed marker.
- [x] **Interpolated value is sensitive**
  A sensitive value interpolated into a string, or passed through a function, assigned to a field declared sensitive, arrives as a sensitive value containing the combined result.
- [x] **Sensitive into plain field rejected in configuration**
  Assigning a sensitive value directly, by interpolation, or through a function to a field not declared sensitive fails validation with an error naming the field.
- [x] **Sensitive output from a module**
  A module output whose value is a sensitive value can be assigned by its caller to a field declared sensitive; assigning it to a plain field fails validation.
- [x] **Partly sensitive output in Go**
  An output whose value is an entity with one sensitive and one plain field, read by application code, holds the sensitive field as a sensitive value and the plain field as a plain value; an output whose whole value is sensitive holds a sensitive value.
- [x] **Sensitive into plain Go field fails**
  Decoding, converting, or looking up into a Go type whose field matching a sensitive value is plain fails with a type error naming the field; the same operation into a type whose field is declared sensitive succeeds.
- [x] **Logs show only the marker**
  Logging an entity holding a known sensitive value through xcl's events, a custom log handler, a plugin log detail, and plain string formatting never produces output containing the real value; each shows the fixed marker.
- [x] **Errors show only the marker**
  An error raised by xcl whose message includes a sensitive value contains the fixed marker and not the real value.
- [x] **Printed and encoded output redacted by default**
  Configuration text and each resource printer format show a sensitive field as the fixed marker by default, and show the real value only when revealing is explicitly requested.
- [x] **Examples print no secrets**
  Running every bundled example produces output that contains none of the passwords or secrets in its configuration.
- [x] **Plugin-author guidance present**
  The plugin-author documentation contains guidance stating that an explicitly unwrapped value is no longer protected and must not be logged or otherwise emitted.
- [x] **Sensitive values docs updated**
  The library's documentation and a page on the site each cover declaring sensitive fields, unwrapping in application code, the sensitive-to-plain errors, and that the application's own JSON serialisation and templates show the fixed marker unless the value is explicitly unwrapped; every example output quoted on the site matches what the examples now produce.

## Technical Approach

- Carry sensitivity through HCL evaluation with cty value marks (the vendored cty supports them; Terraform's `sensitive` works the same way), and enforce the sensitive-to-plain assignment rule on marked values, so references, interpolation, functions and module outputs are all covered by one mechanism.
- Have the sensitive type redact itself through Go's standard formatting and marshalling interfaces (stringer, formatter, structured-log valuer, text and JSON marshalling). Suggested unwrap method name: `Reveal()`, chosen over `Value()` for greppability and to avoid reading as `out.Value…Value()`.
- Have xcl's own reflection-based output (the encoder and the resource printers) recognise the sensitive type explicitly rather than walk into its unexported value.

## Non-Goals

- Protecting against an attacker with access to the process: the protection is against accidental disclosure only.
- Detecting secrets in fields not declared sensitive, for example by field name: a type that uses a plain field for a secret gets no protection and no warning.
- Preventing a leak after an explicit unwrap — for example plugin code that unwraps a value and logs it; this is covered by guidance for plugin authors only.
- Redacting the user's own source text shown in parse and validation diagnostics: it shows only what the user wrote, not evaluated values.
