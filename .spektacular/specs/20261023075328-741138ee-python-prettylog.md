## Overview

A Python program that uses xcl has no ready-made way to watch what xcl is doing; it has to write its own event handling, and even then cannot show what each resource became as it is created. This change adds a ready-made pretty logger to the Python package, modelled on the one Go's examples use: each event appears as a readable, coloured line, each created resource's configuration appears beneath it as it happens, and configuration mistakes appear with the lines in question, all from one line of setup.

## Requirements

- [ ] **One line of setup**
  Users can turn on pretty logging for a configuration in one line, choosing the output stream and the minimum level, with both the synchronous and the asynchronous clients; the level is info when not chosen.
- [ ] **Works with existing logging**
  Users who already configure Python's standard logging can route the pretty logger's output through a logger of their own instead of a bare stream.
- [ ] **Readable event lines**
  The system must write each event at or above the chosen level as one line showing its time, level and message, followed by its source, operation, phase and resource and any remaining event attributes as key=value pairs, with the source, operation and resource highlighted.
- [ ] **Created resources shown as they happen**
  At info and below, the system must write the configuration of each resource beneath the line reporting its creation, as soon as the creation is reported, including values the provider filled in.
- [ ] **Quiet at higher levels**
  When the chosen level is above info, the system must write event lines only, with no configuration.
- [ ] **Configuration mistakes shown with their source**
  Beneath the line reporting an error caused by invalid configuration, the system must write the problem's report: its summary, its file and position, the block and field, the numbered source lines around it with the fault marked, and its detail.
- [ ] **Colour follows the stream**
  The system must colour event lines and configuration when the stream is a terminal and the NO_COLOR convention is not set, and write plain text otherwise.
- [ ] **Level from the environment**
  Users can take the minimum level from an environment variable naming debug, info, warn or error in any letter case, defaulting to info when it is unset or names none of them.
- [ ] **Guidance when resource data is off**
  The system must tell the user how to turn on resource data on events, once per pretty logger, when a resource's configuration cannot be shown because events carry no resource data.
- [ ] **Render failures warn and continue**
  The system must write one warning line for each resource whose configuration cannot be shown, and carry on.
- [ ] **Items without a configuration form are skipped silently**
  The system must show nothing, and write no warning, for variables, outputs and modules.
- [ ] **Documentation**
  The package's README and the xcl website's events page must show the pretty logger's setup and a sample of its output.

## Constraints

- The pretty logger must be part of the xcl Python package, not a separate package or example.
- It must use only the standard library and what the package already depends on.
- The level environment variable must be `XCL_LOG_LEVEL`, the name Go's example uses.
- It must not wait on the operation, or on anything else slower than writing to its stream, inside the event handler, which runs on the loop driving the operation; writing directly to the chosen stream is permitted.
- It must take its colours, formats and error reports from the package's printing support rather than its own copies, so it stays consistent with `design/printing-and-highlighting.md` (source `design`).
- It depends on three specs in this epic being delivered first: the event data level enum (20261023074223-e06f835f-event-data-level-enum), rendering a saved record during an operation (20261023074627-cc23fc08-encode-saved-entity-during-operation), and Python printing (20261023075302-bad71237-printing-and-highlighting-python).

## Acceptance Criteria

- [ ] **Setup and event lines**
  Applying a configuration that creates one resource, with the pretty logger set up in one line on a captured stream and no level chosen, writes one line per event at info or above, each starting with a time and level and containing the event's message and its source, operation, phase and resource.
- [ ] **Configuration beneath creation**
  In the same run, the lines immediately after the creation line hold the created resource's configuration, indented, including a value the provider filled in, written before the next event's line.
- [ ] **Asynchronous client**
  The same run with the asynchronous client produces the same lines apart from timestamps.
- [ ] **Through an existing logger**
  The same run with the pretty logger routed through an application's own standard logger writes the same lines through that logger's handlers.
- [ ] **Warn level is terse**
  The same run at the warn level writes no configuration and no info lines.
- [ ] **Debug level**
  The same run at the debug level additionally writes debug events.
- [ ] **Configuration mistake**
  Applying a configuration with an unsupported block writes the error event's line followed by the report showing the summary, the file and line, and the faulty source lines.
- [ ] **Colour on a terminal only**
  Writing to a pseudo-terminal produces colour codes, with the source, operation and resource values in their highlight colours; writing to a file, or to a pseudo-terminal with NO_COLOR set, produces none.
- [ ] **Level from the environment**
  With `XCL_LOG_LEVEL` set to "debug", "warn", "error", "INFO", unset, and "loud", the level chosen is debug, warn, error, info, info and info respectively.
- [ ] **Guidance without resource data**
  Running with resource data off and two created resources writes event lines and exactly one line explaining how to turn resource data on, and no configuration.
- [ ] **Unrenderable items**
  A configuration with a variable, an output and a module produces no warning and no configuration for them; two resources whose configuration cannot be rendered produce one warning line each, and the run completes.
- [ ] **Docs**
  The package's README and the website's events page show the one-line setup and a sample of the output.

## Technical Approach

- Use Go's `example/prettylog` as the reference for look and layout.
- Build on the package's logging bridge and standard `logging`.
- Render each created resource from the event's saved record.
- Expose it as a small module in the package, for example `xcl.prettylog`, with a handler factory and a level-from-environment helper.
