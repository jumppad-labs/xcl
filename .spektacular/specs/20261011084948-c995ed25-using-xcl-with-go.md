## Overview

A developer adopting XCL has no single walkthrough of its API in their language, only topic pages and generated API docs. This spec adds a guide for each implementation, Go and Python, that takes a developer from an empty program to a working one and explains the API they will use, pointing to the topic pages and API docs for detail.

## Requirements

- [ ] **Guides are reachable from the site**
  Readers can find the Go and Python guides from the site's main navigation and from the home page, and the xcl README points to both.
- [ ] **Using XCL with Go guide**
  The guide walks a Go developer from an empty program to a working one: creating a config, registering entity types, parsing configuration, applying and destroying it, keeping state, and finding entities by address or type.
- [ ] **Using XCL with Python guide**
  The guide walks a Python developer from an empty program to a working one: installing from PyPI, creating a config, registering entity types and functions, using Go plugins, applying and destroying configuration, keeping state, finding entities, and handling errors. It covers the synchronous API first, then the asyncio API and when to use it, such as in web services.
- [ ] **Guides link rather than repeat**
  Each guide links to the existing topic pages (registries, plugins, state and events) and to the generated API docs for detail.
- [ ] **Current behaviour only**
  Every behaviour each guide describes matches the latest tagged xcl release when the guide is published; anything planned but not built is marked as not yet supported rather than described as working.
- [ ] **Positioning and terminology**
  Each guide describes XCL as its own language, calls blocks entities and not resources (except inside Go identifiers), and avoids describing it as a superset of HCL, using the word "interpolation", or comparing it to Terraform.

## Constraints

- The pages must live on the existing xcl.dev site and fit its existing structure and navigation; the site is now the home of the documentation and the README stays an overview.
- Each guide shows only its own language, with no language tabs.
- Python code uses the API defined by the python-support spec (`20261011130709-aa3eb933-python-support`).
- Go code must use the library's current exported names, such as `types.ResourceBase`, even where they still say "resource".

## Acceptance Criteria

- [ ] **Reachable**
  On the built site, the Go and Python guides appear in the main navigation and are linked from the home page, and the xcl README contains a link to each; every one of those links opens the right guide.
- [ ] **Guide is complete**
  Following the guide from top to bottom with only the code it shows produces a Go program that creates a config, registers an entity type, parses configuration, applies it, keeps state between runs, finds an entity by address and by type, and destroys it.
- [ ] **Python guide is complete**
  Following the Python guide from top to bottom with only the code it shows produces a Python program that installs XCL from PyPI, creates a config, registers an entity type and a function, uses a Go plugin, applies configuration, keeps state between runs, finds an entity by address and by type, and destroys it, and that also runs the asyncio version of apply.
- [ ] **Guides link out**
  Each guide links to the registries, plugins, state and events pages and to its language's generated API docs, and every link opens a page that exists.
- [ ] **Matches the current release**
  Each code and XCL example in either guide, when tried by hand against the latest tagged xcl release at the time the guide is published, behaves as the guide says; each feature it marks as not yet supported is indeed unsupported in that release.
- [ ] **Terminology**
  Neither guide contains the words "superset", "interpolation" or "Terraform", and does not use "resource" for a block, except inside Go identifiers.

## Non-Goals

- No automated tests for the examples on the new pages; they are checked by hand.
- No changes to the xcl-vscode highlighter; adding formatting to it and publishing it is separate, later work.
- The guides document the behaviour delivered by the language-surface and python-support specs. Gaps or bugs found while writing them are reported, not fixed in this work.
- No changes to existing topic pages beyond adding links to and from the new guides; adding Python to existing pages belongs to the language reference spec.
