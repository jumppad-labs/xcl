## Overview

Once xcl reaches TypeScript, its programs will still see configuration mistakes as a single line, have no way to style xcl's output or render it for a web page or an image, and must write their own event handling to watch what xcl is doing. This change gives Node programs the same readable output Go and Python have: an error shows the lines in question wherever it ends up, entities and change summaries print in one call, output can be plain, coloured, HTML or an image, and a ready-made pretty logger shows each event and each created entity as it happens. It serves developers building tools and services on the TypeScript package, and the people who read what those tools print.

## Requirements

- [x] **One-call error printing with context**
  Users can print any xcl error to a stream of their choice, or get it as a string, in one call, and a configuration problem is shown as the same report Go prints: severity and summary, location, numbered source lines with the fault marked, and detail. Any other value passed in is printed as its message or text form rather than throwing.
- [x] **Printed and uncaught errors show their report**
  An xcl error holding a configuration problem shows its report when passed to the console and when it goes uncaught.
- [x] **Ordinary messages stay one line**
  An xcl error's message stays one line.
- [x] **Problems reach structured logs**
  An xcl error logged through a JSON logger's standard error handling carries each problem's file, line, column, summary, entity and field, and the plain report, with no logger configuration.
- [x] **Detail wraps to a width**
  A report's detail text wraps at 80 columns by default, as Go does, and users can choose another width or no wrapping.
- [x] **One-call printing of entities and change summaries**
  Users can print an entity as configuration text, and a change summary, in one call each, with the same formatting choices as errors and the four encoding choices: include computed, include empty, reveal sensitive and show references.
- [x] **Choice of output format**
  Users can choose plain text, terminal colour, HTML marked up with classes, HTML with inline styles, or SVG, for any printed output.
- [x] **Websites restyle HTML output**
  Users can generate a stylesheet from a theme, and HTML output carries the same class names as Go's. The package also ships the default stylesheet as a file a site can link.
- [x] **Themes extend the default**
  Users can change the style of any kind of text by giving only the kinds they want to change, written as the same style strings Go uses, with the same fallback from a kind to its category.
- [x] **Themes can be checked**
  Users can validate a theme and are told about any style word that is not recognised; printing with such a theme ignores the unknown word rather than failing.
- [x] **Editor themes can be imported**
  Users can load a VS Code colour theme and use it as a theme.
- [x] **Custom output formats**
  Users can write their own output format that receives the whole labelled text at once and writes to any stream, and use it anywhere a built-in format is accepted.
- [x] **Labelled text for extenders**
  Users can obtain the labelled text (the output split into parts, each labelled with its kind) of an error's report, an entity's configuration text and a change summary.
- [x] **Colour chosen from the stream on request**
  Users can ask for a format chosen from their stream, which picks terminal colour for a terminal unless the NO_COLOR convention is set, and plain text otherwise.
- [x] **Events reach an existing logger**
  Users can send xcl's events to a logger of their own in one line, at the same levels and with the same messages Go's logging bridge uses, for loggers taking fields then message and loggers taking message then fields.
- [x] **Pretty logging in one line**
  Users can turn on pretty logging for a configuration in one line, choosing the output stream and the minimum level; the level is info when not chosen.
- [x] **Pretty logging through an existing logger**
  Users can route the pretty logger's output through a logger of their own instead of a bare stream.
- [x] **Readable event lines**
  The pretty logger writes each event at or above the chosen level as one line showing its time, level and message, followed by its source, operation, phase and entity and any remaining event attributes as key=value pairs, with the source, operation and entity highlighted.
- [x] **Created entities shown as they happen**
  At info and below, the pretty logger writes the configuration of each entity beneath the line reporting its creation, as soon as the creation is reported, including values a provider filled in.
- [x] **Quiet at higher levels**
  When the chosen level is above info, the pretty logger writes no entity configuration. A configuration mistake's report still appears beneath its error line at every level.
- [x] **Configuration mistakes shown with their source**
  Beneath the line reporting an error caused by invalid configuration, the pretty logger writes the problem's report.
- [x] **Colour follows the stream**
  The pretty logger colours event lines and configuration when the stream is a terminal and the NO_COLOR convention is not set, and writes plain text otherwise.
- [x] **Level from the environment**
  Users can ask for the minimum level to be taken from an environment variable naming debug, info, warn or error in any letter case, defaulting to info when it is unset or names none of them.
- [x] **Guidance when entity data is off**
  The pretty logger tells the user how to turn on entity data on events, once per pretty logger, when an entity's configuration cannot be shown because events carry no entity data.
- [x] **Render failures warn and continue**
  The pretty logger writes one warning line for each entity whose configuration cannot be shown for any reason other than missing entity data, and carries on.
- [x] **Items without a configuration form are skipped silently**
  The pretty logger shows nothing, and writes no warning, for variables, outputs and modules.
- [x] **Package documentation**
  The package's README and its parity record cover error printing, how reports appear on uncaught and logged errors, output formats, themes, stylesheet generation, custom formats, logger integration and the pretty logger, with TypeScript examples, and every new public export has a doc comment.

## Constraints

- The work must be built to the design document `printing-and-highlighting.md` in the project's `design` design source, which fixes the TypeScript surface, the split between the core and the language, the style syntax and the logger integration.
- Every built-in format's output must be identical to Go's, checked against the golden files Go and Python are held to.
- The package must not lex configuration or lay out reports itself; it formats the labelled text returned by the bundled xcl engine.
- The package must not add a runtime dependency beyond those the TypeScript core SDK has; pino and winston must not become runtime dependencies; using them in tests is allowed.
- The package must never emit colour unless the user chooses a colour format or asks for a format chosen from the stream. Turning on the pretty logger counts as asking. A report written by Node's console follows the colour setting Node has for that stream, and a report in Node's uncaught-error output is plain text.
- The pretty logger must be part of the `xcl-lang` package, not a separate package or example.
- The pretty logger must take its colours, formats and error reports from the package's printing support rather than its own copies.
- The level environment variable must be `XCL_LOG_LEVEL`, the name Go's example and Python use.
- The pretty logger must not make an operation wait on anything slower than writing to its stream, and must not look up or encode a live entity during an operation.
- The TypeScript core SDK (20261031080136-264e0eab-typescript-core-sdk) must be delivered first.
- The code must live in the `jumppad-labs/xcl-typescript` repository and support Node 22 and later.
- The Go library's and the Python package's behaviour must not change.

## Acceptance Criteria

- [x] **A bad configuration prints as a report**
  A Node program that applies a configuration with an unsupported block on line 7 and prints the rejected error as plain text writes the same report Go writes for that configuration, byte for byte.
- [x] **As a string**
  Getting the same error as a string returns exactly the text that printing it writes.
- [x] **Any error prints**
  Printing a plain JavaScript error writes its message, and printing a value that is not an error writes its text form, without throwing.
- [x] **Console and uncaught errors**
  Passing the error to `console.error` writes the report, and a program that lets it go uncaught writes the report to standard error before exiting with a failure status, on Node 22, 24 and 26.
- [x] **Message is one line**
  The error's `message` holds no newline.
- [x] **JSON logs carry problems**
  Logging the error through pino's standard error serializer and through winston's error format, with no other configuration, produces JSON holding each problem's file, line, column, summary, entity and field, and the plain report.
- [x] **Wrapping**
  A report whose detail is longer than 80 columns wraps at 80 by default, at a chosen width when one is given, and not at all when no wrapping is asked for, matching Go's output in each case.
- [x] **Entities and diffs print**
  Printing an entity gives the same text as Go's encoder for each combination of the four encoding choices, and printing a change summary gives the same text as Go.
- [x] **Formats match Go**
  For the shared reference outputs, each of plain, terminal, HTML with classes, HTML with inline styles and SVG output is byte-for-byte equal to Go's, for an error report, an entity and a change summary.
- [x] **Stylesheet**
  The stylesheet generated from the default theme is byte-for-byte equal to Go's, and the file shipped in the package holds the same text and can be imported by its published path. A stylesheet generated from a theme that changes one kind's style differs from the default only in that kind's rule.
- [x] **Theme changes one kind**
  A theme giving a new style for line comments and nothing else renders line comments in that style, other comments in the default style and everything else as the default theme does. A kind given no style falls back to its category.
- [x] **Theme validation**
  Validating a theme holding the unknown style word `blinky` reports that word, and printing with that theme succeeds and ignores it.
- [x] **VS Code theme**
  Loading a VS Code colour theme file gives a theme that renders a keyword in the file's keyword colour.
- [x] **Custom format**
  A user-written format receives the whole labelled text in one call and its output is written to the chosen stream, for errors, entities and change summaries.
- [x] **Labelled text**
  The labelled text of an error's report, an entity's configuration text and a change summary each concatenates to the plain text of that output, and each part carries its kind.
- [x] **Colour from the stream**
  The format chosen from a terminal stream is terminal colour, from a terminal stream with `NO_COLOR` set is plain, and from a non-terminal stream is plain. Printing with no format chosen writes no colour on a terminal.
- [x] **Events to a logger**
  With events sent to a pino logger in one line and to a winston logger in one line, an apply produces one log record per event at the same level and with the same message as Go's logging bridge, and the event's details are in the record's fields.
- [x] **Pretty logger setup and event lines**
  Applying a configuration that creates one entity, with the pretty logger set up in one line on a captured stream and no level chosen, writes one line per event at info or above, each starting with a time and level and containing the event's message, its source, operation, phase and entity, and any remaining attributes as key=value pairs.
- [x] **Configuration beneath creation**
  In the same run, the lines immediately after the creation line hold the created entity's configuration, indented, including a value a provider filled in, written before the next event's line.
- [x] **Through an existing logger**
  The same run routed through an application's own logger writes the same lines through that logger.
- [x] **Warn level is terse**
  The same run at the warn level writes no configuration and no info lines.
- [x] **Debug level**
  The same run at the debug level additionally writes debug events.
- [x] **Configuration mistake in the pretty logger**
  Applying a configuration with an unsupported block writes the error event's line followed by the report showing the summary, the file and line, and the faulty source lines.
- [x] **Pretty logger colour**
  On a terminal stream the event lines and configuration hold colour codes; with `NO_COLOR` set, or on a captured stream, they hold none.
- [x] **Level variable**
  When a program asks for the level from the environment, `XCL_LOG_LEVEL` set to `WARN` makes the pretty logger behave as at the warn level, and an unrecognised word makes it behave as at info. A program that does not ask ignores the variable.
- [x] **Guidance once**
  With events carrying no entity data, an apply creating two entities writes the guidance on turning entity data on exactly once, and writes no configuration and no warning lines.
- [x] **Render failure**
  When one entity's configuration cannot be shown, the pretty logger writes one warning line for it, the apply succeeds and later entities are still shown.
- [x] **Skipped items**
  A configuration with a variable, an output and a module writes no configuration and no warning for them.
- [x] **An operation is not slowed**
  With the pretty logger on, a timer on the same event loop keeps firing during an apply with a 99th-percentile delay under 50 ms.
- [x] **Docs present**
  The README and parity record each cover every topic named in the documentation requirement, and every new public export has a doc comment.

## Technical Approach

- Shape the pretty logger after xcl-python's `prettylog`, for which the design has no TypeScript section.
- Implement the console report with `util.inspect.custom`, letting colour follow the option Node's console sets for its stream. Node's uncaught-error printing does not call it, so carry the plain report in the error's `stack`, between the first line and the stack frames, with no process listener.
- Make `problems` and `report` enumerable on the error so pino's `err` serializer and winston's `format.errors()` carry them.
- Have the pretty logger read entity data from events and render saved records, as Python does.
- Ship `xcl.css` through the package's `exports` map.
- Risk: an async `console` destination or a piped stream reordering a report relative to event lines.
