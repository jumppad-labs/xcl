## Overview

Applications that use xcl for configuration often want everything a configuration declares gathered into one structure of their own, such as a list of every server and every mount point, ready to pass around. Today they have to ask for each kind of block separately and assemble that structure by hand. This feature lets an application hand xcl its own structure and have it filled in one call, with each field picking up the blocks of its kind in the order they were written. Developers who use xcl to read plain configuration get simpler setup code, and adding a new kind of block becomes a matter of adding a field.

## Requirements

- [x] **Fill a structure in one call**
  Developers can give the configuration a structure of their own and have its fields filled from the blocks the configuration declares, in a single call.
- [x] **A collection field receives every block of its type**
  A field that holds a collection of a registered block type receives every block of that type the configuration declares, in the order they were written, and nothing else.
- [x] **The same blocks a typed lookup returns**
  For each collection field, the blocks received are exactly the ones the existing "every block of this type" lookup returns for the same type, including disabled blocks. The two can never disagree.
- [x] **The configuration's own blocks, not copies**
  Each block placed in the structure is the same instance the configuration holds, so it matches what any other lookup on that configuration returns.
- [x] **A single-block field is filled when exactly one exists**
  A field that holds one block of a registered type is set when the configuration declares exactly one block of that type, and left empty when it declares none.
- [x] **More than one block for a single-block field is an error**
  When a single-block field's type is declared more than once, the call fails with the same "not unique" error the existing single-block lookup returns, and that error reports how many were found.
- [x] **Fields are matched by type, not by name**
  Which blocks a field receives depends only on the block type it holds. Field names play no part.
- [x] **Other fields are left alone**
  Fields whose type is not a registered block type keep whatever value they had before the call, so the structure can hold the application's own settings alongside configuration.
- [x] **An unusable target is an error**
  Passing a target that cannot be filled fails with an error, and neither the target nor the configuration is changed.
- [x] **Nothing processed yet gives an empty result, not an error**
  On a configuration that has not yet been loaded and processed, and so holds no blocks, the call succeeds, leaving collection fields empty and single-block fields unset.
- [x] **Referenced blocks arrive filled in**
  A nested block that references another registered block as a whole receives that block's values, however the receiving field holds it.
- [x] **Documented with an example**
  The project's user-facing documentation shows the feature filling a structure from a configuration.

## Constraints

- **The call must be named `Decode`.** It is offered as a method on the configuration and as a package-level function taking the configuration, in the same forms as the existing lookups.
- **Must work on every Go version the project currently supports.**
- **No struct tags or other annotations are read.** Which blocks a field receives is decided by its type alone.
- **Only two field shapes are filled:** a slice of pointers to a registered type (`[]*T`) and a single pointer to one (`*T`). Every other field is left untouched.
- **No change to existing public behaviour.** The existing lookups keep their current signatures and results.
- **Project test conventions apply.** Tests use testify `require`, never table-driven tests, and positive and negative cases go in separate test functions (project policy).

## Acceptance Criteria

In these criteria, A and B are block types registered with the configuration, and U is a structure type that is not registered.

- [x] **Collection fields filled from a configuration**
  After applying a configuration that declares two blocks of type A and one of type B, a structure with a collection-of-A field and a collection-of-B field holds both A blocks and the B block, each with the attribute values written in the configuration.
- [x] **Declaration order is preserved**
  When the two A blocks are written in the opposite order, the collection-of-A field comes back in that opposite order.
- [x] **Matches the typed lookup**
  For every collection field, the blocks received are equal, element for element, to what the existing "every block of this type" lookup returns for the same configuration. This includes a block marked disabled.
- [x] **Same instances as other lookups**
  A block taken from the filled structure is the same instance that looking it up by its address returns; a change made through one is visible through the other.
- [x] **Single-block field with exactly one block**
  A single-B field is set to the B block when the configuration declares exactly one.
- [x] **Single-block field with no blocks**
  A single-block field whose type the configuration never declares is left unset, and the call succeeds.
- [x] **Single-block field with several blocks**
  A single-A field, given a configuration with two A blocks, makes the call fail with an error that matches the existing "not unique" error and reports a count of 2.
- [x] **Field names do not matter**
  Renaming a collection field to any other name gives the same contents.
- [x] **Unrelated fields untouched**
  A plain value field and a field of type U, both set beforehand, hold the same values after the call.
- [x] **Unusable targets rejected**
  Passing a structure by value, a nil pointer, or a pointer to something that isn't a structure each fails with an error, and neither the target nor the configuration is changed.
- [x] **Empty before processing**
  On a configuration that has not been loaded and processed, the call succeeds; collection fields come back empty and single-block fields unset.
- [x] **Both call forms behave the same**
  The method form and the package-level form give equal structures and equal errors for the same inputs.
- [x] **Whole-block references arrive filled in**
  When a nested block inside a B block references an A block as a whole, the filled B holds that A block's attribute values, whether the receiving field holds A directly or as a pointer.
- [x] **Docs show an example**
  The README and the docs site's configuration-only example page each show a configuration and the call that fills a structure from it.

## Technical Approach

- **Build on the existing typed lookups.** Prefer resolving each field's block type through the same path the "every block of this type" lookup already uses.
- **Prefer working from the already-parsed blocks** the configuration holds after it has been processed, rather than re-reading configuration files.
- **Known risk:** a field holding a pointer to a referenced block, and a reference to a registered non-`resource` block from inside a nested block, appear to work today but have no test coverage. Expect the plan to add coverage first, and a fix if needed.
- **Documentation:** the README and the docs site's configuration-only example page are the natural homes, and they may use the server/mount configuration that motivated this feature as their worked example.

## Success Metrics

- Filling an application structure from a configuration takes one call, however many registered block types the structure holds, where today it takes one lookup per type plus hand assembly.
- Adding a new registered block type to an application's configuration needs only a new field on its structure, with no new lookup code.
- Every shipped example program that assembles configuration from several block types does so with the new call, with no per-type lookups for that assembly.

## Non-Goals

- Recursing into nested aggregate structures: a field that is itself a structure to be filled is left alone, not decoded into.
- Selecting blocks by subtype or by module; a field receives every block of its type.
- Writing a filled structure back out as configuration text, or saving it to state.
