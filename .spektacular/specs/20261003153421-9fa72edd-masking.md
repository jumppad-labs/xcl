## Overview

With sensitive values in place, state stores them in plain text and events can only ever show the fixed marker. This introduces pluggable masking: state encrypts sensitive values when a key is supplied and warns when it cannot, events redact them by default with the option to hash, encrypt, omit or send them, and developers can supply their own masking.

## Requirements

- [x] **Masking is pluggable**
  Developers can choose how sensitive values are masked for state and for events, and can supply their own masking.
- [x] **Built-in maskers are provided**
  xcl provides a reversible symmetric-encryption masker, a one-way keyed-hash masker, a masker that omits the value, and a masker that replaces it with a fixed marker.
- [x] **Masked data records how it was masked**
  Masked data identifies which masker produced it, so a reader can tell whether it can be recovered.
- [x] **State encrypts sensitive values when configured**
  With a reversible state masker configured, state never holds a sensitive value in plain text, and xcl loads it back to the real value.
- [x] **State without a masker warns**
  With no state masker configured, state holds sensitive values in plain text and xcl emits a warning saying so.
- [x] **State refuses a one-way masker**
  Configuring a state masker that cannot recover the value is rejected when xcl is set up with that masker.
- [x] **Events redact by default**
  Resource data on events shows sensitive values as the fixed marker unless the developer chooses another masker.
- [x] **Events can carry real values on request**
  Developers can explicitly turn event masking off, after which events carry real sensitive values.
- [x] **Masking is documented**
  The library's documentation and the documentation site's events guide and a state-masking page describe the maskers, how to configure them for state and events, the plaintext-state warning, and how to turn event masking off.
- [x] **Errors stay redacted whatever the event masking**
  Error messages produced by xcl show sensitive values only as the fixed marker even when event masking is turned off.

## Constraints

- Sensitivity must be declared with a sensitive Go type, `types.Sensitive[T]`, on the field — not with a struct-tag option — so the value protects itself wherever it is formatted or serialised, including in loggers xcl does not own.
- Masking must be pluggable through an extensible interface named `Masker`, which developers can implement themselves.
- Configuration options must be named `WithStateMask`, `WithEventMask` and `WithNoEventMask`.
- Built-in maskers must be named explicitly for their algorithm: `mask.EncryptAES256GCM` (AES-256-GCM, reversible), `mask.HashHMACSHA256` (keyed HMAC-SHA256, one-way), plus `mask.Omit` and `mask.Redact`.
- A key must not be required to use xcl: state must work without a state masker.

## Acceptance Criteria

- [x] **Custom masker is used**
  A developer-supplied masker configured for state, and another for events, are each used for their destination: state and event data contain that masker's output for each sensitive value.
- [x] **Built-in maskers behave as named**
  The encryption masker's output differs from the input and is recovered to the original with the same key and fails to recover with a different key; the keyed-hash masker gives the same output for the same input and key and a different output for a different key; the omit masker leaves no value; the redact masker gives the fixed marker.
- [x] **Masked data names its masker**
  Masked state and event data identify which masker produced each sensitive value; reading data produced by a one-way masker reports the value as unrecoverable rather than returning a wrong value.
- [x] **State holds no plain secret with encryption**
  With the encryption masker configured for state, after applying a configuration containing a known sensitive value, the state file does not contain that value anywhere, and a new configuration loading that state with the same key reads back the real value.
- [x] **Plain state warns**
  With no state masker configured, applying a configuration containing a sensitive value writes it to state in plain text and emits a warning event saying sensitive values are stored unencrypted; a configuration with no sensitive values emits no such warning.
- [x] **One-way state masker rejected**
  Setting up xcl with a one-way masker for state fails with an error saying the state masker must be reversible.
- [x] **Events redact by default**
  With events set to carry resource data and no event masker chosen, every event carrying resource data shows each sensitive value as the fixed marker and never the real value.
- [x] **Event masking can be turned off**
  With event masking explicitly turned off, events carrying resource data contain the real sensitive values.
- [x] **Masking docs updated**
  The library's documentation, the site's events guide and a site page on state masking each cover configuring state and event maskers, the built-in maskers, the plaintext-state warning, and turning event masking off.
- [x] **Errors redacted with event masking off**
  With event masking explicitly turned off, an xcl error whose message includes a sensitive value contains the fixed marker and not the real value.

## Technical Approach

- Known risk: Go's JSON marshalling carries no per-call context, so a sensitive value cannot tell on its own whether it is being written to state or to an event; choose the masker per serialisation call rather than through global state.
- Expect event data and state to stop being byte-identical once events are masked and state is encrypted.

## Non-Goals

- Backwards compatibility with existing state files: state written by earlier versions does not have to load.
- Whole-file encryption of state: only sensitive values are masked in state; whole-file encryption may come later.
