## Overview

xcl's plugin example is rewritten as a real project modelled on Jumppad. An external Docker plugin creates real Docker networks and containers, and an in-process template plugin renders Handlebars templates to files. Each plugin ships with the tests a plugin author would write: unit tests against a mocked Docker client or a temporary directory, and real-Docker tests that skip cleanly when no engine is available. xcl's library gains tested support for plugin block types with no subtype, which the `template` block needs. Plugin developers get an example they can run for real and copy as their own project, and the README, the plugins guide and the documentation website are updated to match it.

## Conventions

- **Testing & Mocking (testify `require`, Mockery, no table-driven tests, positive and negative apart, tests live with their code, each example has its own `smoke_test.go`)**: governs every test in the rewritten example and the new library tests. It is why the Docker client mock is generated by Mockery and why the smoke test builds and runs the real binary.
- **Code style (gofmt, go vet, import grouping, small focused interfaces, `any`)**: the Docker `Client` interface is deliberately small, and every new Go file follows the standard style.
- **Dependencies (prefer stdlib, document third-party deps, pin versions)**: the example's `go.mod` pins the Docker SDK and go-connections to Jumppad's versions and raymond to xcl's. The smoke test uses `os/exec` only.
- **Patterns & Architecture (dependency injection, `context.Context`)**: providers receive the Docker client as an injected field, and every Docker call takes the provider call's context.
- **Development standards (structured logs)**: providers log through `plugins.Logger(ctx)` with key/value pairs.
- **Shared error types live in the `errors` package**: the library change adds no new sentinel. Error-message fixes reuse `types.TypeKey`. Recorded so that any new shared error goes there.
- **Never modify dependency packages**: the example points at xcl with a `replace`, and the Docker SDK is used as published.
- **Project structure (`/cmd` for main applications)**: the external plugin binary lives at `example/plugin/cmd/docker-plugin`.

## Architecture & Design Decisions

The work spans two repos. In `xclconfig` (`/home/nicj/code/github.com/jumppad-labs/xcl`) it confirms and hardens plugin types registered with no subtype (`plugins/`), rewrites `example/plugin` as a self-contained Go module laid out like a real plugin project, and updates the README and `docs/plugins.md`. In `xcl-website` (`/home/nicj/code/github.com/jumppad-labs/xcl-website`) it rewrites the plugin example page and the plugin-logging, events and index passages that quote or describe the old example. It builds on the e2e plan (`20261006071142-506b8289`), which must land first. That plan makes `example/plugin` its own module (`go 1.25.0`, with `replace` directives to `../..` and `../prettylog`), gives it a standard-library smoke test, and makes the e2e suite run its tests through `TestPluginExampleTestsPass`.

**Library: types with no subtype, verified first.** The spec flags this as its main risk. Research shows the pieces mostly exist already. The registry decides the label count from the first registration of a keyword (`plugins/registry/plugin_registry.go:162-190`), the parser takes a single name label when there is no subtype (`internal/parser/parser.go:800-846`), and addresses print as `type.name` (`internal/resources/fqrn.go:293`). What is missing is small:
- A no-subtype provider loses its `provider=` log tag, because the adapter is named after the subtype (`plugins/plugin.go:70`). The fix falls back to the type name.
- Several error messages join `type + "." + subtype` and leave a trailing dot. They switch to `types.TypeKey`.
- Nothing tests the path, either in-process or over gRPC. Tests are added for both.

These changes are additive. Every subtyped registration behaves exactly as before, and the existing tests are the regression guard. This is the first milestone, so a surprise surfaces before any example code depends on it.

**The example as a plugin project.** `example/plugin` is laid out the way a plugin author would lay out their own repository, with tests next to the code they test (`conventions/testing-and-mocking.md`):
- `docker/` is the Docker plugin package. It holds:
  - the thin `Client` interface, covering only the Docker SDK methods the providers call: network create, inspect and remove; image list and pull; container create, start, stop, remove and inspect; network connect; and ping. `*client.Client` from `github.com/docker/docker v28.5.2+incompatible`, the version Jumppad pins, satisfies it.
  - `NewClient`, which uses `client.WithHostFromEnv()` and `client.WithAPIVersionNegotiation()` as Jumppad does.
  - `Ping`, the reachability check.
  - the `Network` and `Container` block types.
  - their providers, which hold the client as a field.
  - the plugin, which registers `("docker","network")` and `("docker","container")`.
  - a Mockery-generated `docker/mocks.MockClient`.
- `cmd/docker-plugin/` is the external plugin binary that serves it over go-plugin.
- `template/` is the in-process template plugin. It registers `("template","")` and renders with `github.com/infinytum/raymond/v2 v2.0.5`, the Handlebars library xcl already uses, keeping the `quote` and `trim` helpers from `internal/functions/functions.go:286`.
- `main.go` is the application. It checks Docker with `docker.Ping`, registers the template plugin and the Docker plugin binary, applies `./config`, prints what it created, destroys everything and stops the plugin host.

The configuration declares `docker "network" "app"`, a `docker "container" "web"` that joins it through a nested `network` block, and a `template "welcome"`. The template's variables read the container's computed IP address and the network's name, so a computed value crosses from the external plugin to the in-process one.

**No test-only seams, Docker-aware tests.** `main` is split into functions it calls itself:
- `apply(registry, handler, configDir, dockerPlugin, stateDir) (*xcl.Config, error)`
- `report(out, config) error`

Every parameter is one `main` passes, so the wiring test calls `apply` the same way `main` does. The tests that need a real engine call `docker.Ping` and `t.Skip` when it fails. These are the docker package's integration tests (a network and an attached container appear in Docker and disappear on destroy), the wiring test, and the smoke test, which builds the plugin into `build/` and runs the program with no arguments. Provider unit tests use the mock or a temporary directory and never touch Docker. Positive and negative cases are in separate functions, and none is table-driven.

**Why this direction.** It mirrors Jumppad's structure but keeps it to example size:
- one thin interface instead of Jumppad's ~40-method `Docker` plus `ContainerTasks`;
- the first network attached at container create instead of Jumppad's connect-then-disconnect dance;
- an availability skip instead of `-short`;
- an exported `Ping` that the program uses, instead of test helpers duplicated per package.

The rejected options and their evidence are in `research.md#alternatives-considered-and-rejected`.

## Component Breakdown

- **Plugin type registration (changed, library).** Plugins can register a block type that has no subtype, written as `template "name" {}`. That path is now tested both in-process and across the external-plugin boundary. A provider registered without a subtype is still tagged in logs, using its type name. Error messages name such a type without a trailing separator. Types registered with a subtype behave exactly as before.
- **Docker client interface (new, example).** A small interface that mirrors only the Docker Engine SDK methods the Docker providers call. The real SDK client satisfies it, and a constructor builds that client from the environment. A ping helper built on it tells the application, and the tests, whether a Docker engine is reachable. A Mockery-generated mock of the interface stands in for Docker in the provider unit tests.
- **Docker network and container providers (new, example).** These own the lifecycle of the `docker "network"` and `docker "container"` block types. The network provider creates a labelled bridge network and removes it on destroy. The container provider pulls the image if it is not present, then creates and starts the container on the networks its `network` blocks name. It records the container's ID and its address on the first network, then stops and removes the container on destroy. Both hold the Docker client as a field and log through the provider call's logger.
- **Docker plugin and its binary (new, example).** The plugin registers both Docker block types with their providers and builds the real client when it initialises. A small program serves the plugin as an external plugin binary, which the application starts as a separate process.
- **Template provider and plugin (new, example).** These own the `template` block type, which has no subtype. The provider renders a Handlebars source with the block's variables, using the same helpers xcl's template function offers. It writes the result to the destination, creating parent directories, and removes the file on destroy. The plugin is compiled into the application.
- **Application (rewritten, example).** The program a reader runs. It checks that Docker is reachable, registers the in-process template plugin and the Docker plugin binary, and applies its configuration. It prints the networks, containers and rendered templates it created, then destroys everything and stops the plugin process. Its steps are ordinary functions the program calls, so its tests drive the same code path without any test-only entry point.
- **Example configuration (rewritten, example).** A network, a container that joins it, and a template whose variables read the container's computed address and the network's name. This shows a computed value crossing from the external plugin to the in-process one. A variable sets where the template is written.
- **Example tests (rewritten, example).**
  - Unit tests per provider: the Docker providers against the mock, the template provider against a temporary directory.
  - Integration tests that create and remove real Docker resources.
  - A wiring test that applies the configuration through both plugins.
  - A smoke test that builds the plugin and the program and runs the program with its defaults.
  - Every test that needs Docker skips when no engine is reachable.
- **Example module and build files (changed, example).** The example's module file gains the Docker SDK and the Handlebars library, pinned. A Mockery configuration generates the client mock. The Makefile builds the plugin binary, regenerates mocks, runs and tests the example. The old in-process, external, resources and module code is removed.
- **Library documentation (changed).** The README's plugins section and the plugins guide describe the Docker and template plugins, and the README stops linking a module the example no longer has. This spec does not edit `CHANGELOG.md`; the epic's changelog entry is written once after all its specs are implemented.
- **Documentation website (changed, `xcl-website`).** The plugin example page is rewritten around the new example. The plugin-logging, events and home pages lose every snippet and claim about the old example and gain matching ones from the new. The state-masking page is not touched: its call to action belongs to the configuration-example spec.
- **End-to-end suite (unchanged, reused).** Its existing runner test runs the rewritten example's tests. Its own fixtures are copies of the old example, so the rewrite does not affect them.

## Data Structures & Interfaces

**Library.** No public type or signature changes. `plugins.RegisterResourceProvider(p, logger, state, typeName, subTypeName, instance, provider)` already accepts `subTypeName == ""`; this plan makes that a supported, tested contract. Such a type is written `<type> "<name>" {}`, addressed `<type>.<name>`, logged with `provider=<type>`, and keyed `<type>` in messages. A keyword cannot be registered both with and without a subtype (the existing `TypeFormError`).

**Docker client interface (example, `docker` package).** The seam between the providers and Docker. Each method's signature is copied exactly from `github.com/docker/docker/client` v28.5.2, so `*client.Client` satisfies it unchanged:

```go
type Client interface {
    Ping(ctx context.Context) (types.Ping, error)
    NetworkCreate(ctx context.Context, name string, options network.CreateOptions) (network.CreateResponse, error)
    NetworkInspect(ctx context.Context, networkID string, options network.InspectOptions) (network.Inspect, error)
    NetworkRemove(ctx context.Context, networkID string) error
    NetworkConnect(ctx context.Context, networkID, containerID string, config *network.EndpointSettings) error
    ImageList(ctx context.Context, options image.ListOptions) ([]image.Summary, error)
    ImagePull(ctx context.Context, ref string, options image.PullOptions) (io.ReadCloser, error)
    ContainerCreate(ctx context.Context, config *container.Config, hostConfig *container.HostConfig,
        networkingConfig *network.NetworkingConfig, platform *ocispec.Platform, containerName string) (container.CreateResponse, error)
    ContainerStart(ctx context.Context, containerID string, options container.StartOptions) error
    ContainerStop(ctx context.Context, containerID string, options container.StopOptions) error
    ContainerRemove(ctx context.Context, containerID string, options container.RemoveOptions) error
    ContainerInspect(ctx context.Context, containerID string) (container.InspectResponse, error)
}

func NewClient() (Client, error)      // client.NewClientWithOpts(client.WithHostFromEnv(), client.WithAPIVersionNegotiation())
func Ping(ctx context.Context) error // NewClient + Client.Ping; error when no engine is reachable
```

`mocks.MockClient` is generated from it by Mockery (testify template), the same configuration shape as xcl's root `.mockery.yml`.

**Block types (example).** The Docker types are owned by the `docker` package and the template type by the `template` package. Each embeds `types.ResourceBase` with `xcl:",remain"` and uses `xcl` and `json` tags. The main program decodes into the same types with `xcl.Find`/`FindByType`.

```go
// docker "network" "<name>"
type Network struct {
    types.ResourceBase `xcl:",remain"`
    Subnet   string `xcl:"subnet,optional"`             // optional IPAM subnet
    DockerID string `xcl:"docker_id,optional,computed"` // set on create
}

// docker "container" "<name>"
type Container struct {
    types.ResourceBase `xcl:",remain"`
    Image       string                `xcl:"image"`
    Command     []string              `xcl:"command,optional"`
    Environment map[string]string     `xcl:"environment,optional"`
    Networks    []NetworkAttachment   `xcl:"network,block"`               // repeated nested block
    DockerID    string                `xcl:"docker_id,optional,computed"`
    IPAddress   string                `xcl:"ip_address,optional,computed"` // address on the first network
}

type NetworkAttachment struct {
    Name    string   `xcl:"name"`              // Docker name of the network, i.e. docker.network.app.name
    Aliases []string `xcl:"aliases,optional"`
}

// template "<name>"   (no subtype)
type Template struct {
    types.ResourceBase `xcl:",remain"`
    Source      string            `xcl:"source"`              // Handlebars text
    Destination string            `xcl:"destination"`         // file path to write
    Variables   map[string]string `xcl:"variables,optional"`
}
```

**Docker naming and labels.** The Docker object's name is the block's `Meta.Name`. It carries labels `created_by=xcl-example-plugin` and `xcl_id=<Meta.ID>`, so a reader can filter Docker's listings for the objects the example created.

**Application functions (example, `main` package).** These are not test seams; `main` calls each of them:

```go
func apply(r *registry.PluginRegistry, handler xcl.EventHandler, configDir, dockerPlugin, stateDir string) (*xcl.Config, error)
func report(out io.Writer, c *xcl.Config) error
```

`main` takes the optional arguments `[config dir] [docker plugin binary]`, which default to `./config` and `./build/docker-plugin`. The configuration variable `output_dir`, overridable as `HCL_VAR_output_dir`, sets where the template is written and defaults to `./build/rendered`.

## Implementation Detail

**A plugin project, not a demo.** The plugin example stops being one program with an inner and an outer plugin. It becomes a small project made of independent packages: a Docker plugin package, a template plugin package, a `cmd` binary that serves the Docker plugin, and the application that uses both. Each package carries its own tests. A reader can lift `docker/` and `cmd/docker-plugin/` into their own repository and have a working, tested external plugin. That is the shape the spec asks for when it says "copy as their own project". The postgres/redis/app/ingress code, the shared `resources` package and the configuration module all go away. Block types move into the plugin that owns them, because a real plugin author ships their types with their provider.

**A new pattern for xcl examples: an injected external client with a generated mock.** Nothing in xcl's examples talks to a real system today. The Docker providers introduce the pattern Jumppad uses:
- a narrow interface over the SDK;
- the real client injected as a provider field when the plugin initialises;
- a Mockery mock injected directly in unit tests, in the same package.

Unit tests assert on the arguments the provider passes to Docker and on the computed fields it fills from Docker's responses. Separate integration tests assert on what Docker actually holds afterwards. The example module carries its own Mockery configuration in the same shape as xcl's root one, and a Makefile target regenerates the mock.

**Following existing patterns.**
- Providers embed `plugins.DefaultChanged` and log through `plugins.Logger(ctx)`.
- The external binary serves through go-plugin with xcl's handshake.
- The application registers one in-process plugin and one plugin binary on a registry it shares with the prettylog receiver.
- The test package builds the plugin binary once in `TestMain`.

All of this follows today's plugin example. What changes is that every file is something a plugin author would actually write.

**Environment-aware tests.** Tests fall into two kinds, which a reader can tell apart by name and by their first line:
- Tests that need nothing external: mock-backed provider tests, and template tests against a temporary directory.
- Tests that need a Docker engine: they call the same `Ping` the application uses and skip with a clear reason when it fails.

On a machine without Docker, the example's tests pass with the Docker-dependent ones reported as skipped. In CI, where Docker is present, they all run. Integration tests use their own resource names and remove what they create through `t.Cleanup`, so a failed run does not leave Docker objects behind.

**The library change is invisible to existing users.** Supporting a plugin type with no subtype is mostly already there. The visible differences are a `provider=` tag on logs from such providers that was previously missing, and error messages without a dangling separator. New tests pin the in-process path and the gRPC path so the behaviour cannot regress silently.

**Documentation follows the code.** Every snippet on the website and in the README that comes from the example is re-copied from the new source after the example is final. The website has no automated snippet check, so the final comparison is a manual review. Prose that names the old types (`postgres`, `redis`, `app`, `ingress`, `ExamplePlugin`, `external`) is rewritten wherever it describes the example. Generic illustrations that only happen to use postgres are left alone.

## Testing Approach

**Kinds of tests.**
- **Library unit and integration tests (xcl).** These cover plugin types registered without a subtype: in-process through the direct plugin host, and across the gRPC boundary. They check that such a type parses from `<type> "<name>" {}`, applies, is addressed `<type>.<name>`, and tags its provider logs with the type. A separate negative test checks that a block giving a subtype label for such a type is rejected. The existing library suite is the regression guard for subtyped types and must pass unchanged.
- **Provider unit tests (example, no Docker).** The Docker network and container providers are tested against the Mockery mock of the client. They check:
  - the arguments sent to Docker: name, labels, subnet, image, network attachment and aliases;
  - the computed fields filled from Docker's responses;
  - that an image pull is skipped when the image is already present;
  - that each Docker error comes back as a provider error.

  The template provider is tested against a temporary directory: variables are substituted, parent directories are created, the helpers work, the file is removed on destroy, and destroying a missing file succeeds. An unparseable template is a separate negative test.
- **Docker integration tests (example, real Docker).**
  - A network the provider creates is visible in Docker with its labels.
  - A container the provider creates is running and attached to that network.
  - Destroying each removes it.
- **Wiring tests (example, real Docker).** The application's own `apply` registers both plugins and applies a configuration that uses them. The tests find the network, the container and the template among the entities, and find the rendered file with the container's address and the network's name substituted. A separate test checks that destroying removes the file and the Docker objects.
- **Smoke test (example, real Docker).** It builds the plugin binary into the default location and builds the program. It then runs the program with no arguments, the way `make run` does, and checks that it exits successfully, reports what it created, and reports everything destroyed.

**Where coverage concentrates.** The providers carry the example's real logic, so they get the most unit tests, and every Docker call path has one positive and one error test. The integration and wiring tests are few, because each one costs a container start. They exist to prove that the mock-backed assumptions hold against a real engine.

**Load-bearing assertions.**
- Without a Docker engine, every provider unit test runs and passes, and every Docker-dependent test reports as skipped, not failed, so the module's tests pass.
- With Docker, applying the example creates a network and an attached container visible in Docker and renders the template. Destroying removes all three.
- A plugin type with no subtype works in-process and across the plugin process boundary. Types with a subtype are unchanged.
- The application exposes no function, parameter or return value that only its tests use.

**Fit with existing conventions.**
- Tests use testify `require`, `Test<Subject><Behaviour>` names, one behaviour per function, and no tables, with positive and negative cases in separate functions.
- Mocks come from Mockery.
- Library tests use `internal/testutil` where they need an event recorder. Example tests use only public packages and the standard library.
- The plugin binary is built once in `TestMain`, as today.
- Docker-dependent tests clean up through `t.Cleanup`.

**Deliberate gaps.**
- There is no test for update or refresh behaviour, because change detection is a non-goal.
- No test compares website snippets to source, because the website has no test harness. That check is manual, below.
- There is no test of image-pull progress output.

**Success metrics.** The spec defines no success metrics beyond its acceptance criteria, so there are none to verify separately.

**Acceptance checks a person makes.**
- Copy `example/plugin` out of the repository, replace the `replace` directives with a published xcl version (and prettylog), and confirm it builds and its tests pass, or skip where Docker is absent. **Manual — captured in the implementation test plan.**
- Run the example's tests on a machine with no Docker engine and confirm the Docker-dependent tests report as skipped and the run passes. **Manual — captured in the implementation test plan.**
- With Docker running, run the example and confirm in Docker's network and container listings (filtered on the example's label) that the network and container exist during the run and are gone afterwards. **Manual — captured in the implementation test plan.**
- Review that the example's program exposes no test-only function, parameter or return value. **Manual — captured in the implementation test plan.**
- Compare every website snippet taken from the plugin example (plugins, plugin-logging, events and home pages), and the README and `docs/plugins.md` passages, against the final source. **Manual — captured in the implementation test plan.**

## Open Questions

- **Does an external plugin type's repeated nested block survive the plugin-type rebuild on the host?** This depends on `reflect.StructOf` handling the nested block's generated struct, which only exercising it reveals (knowledge `gotchas/plugin-types-rebuilt-with-structof.md`). The first task tests it. If it fails and a backwards-compatible library fix is not straightforward, STOP and ask whether to fix the library or switch the container's networks to a list attribute.
- **Does the Docker SDK v28.5.2 dependency graph keep the example module at `go 1.25.0`?** This depends on the minimum Go versions of the SDK's transitive dependencies, which show only when `go mod tidy` runs. If tidy raises the `go` directive, STOP and ask, because the e2e plan fixes `go 1.25.0` for every example and CI builds the examples on Go 1.25.0.
- **Does the local engine's Docker compatibility API accept every call the providers make?** This depends on the engine. The development machine runs Podman behind `/var/run/docker.sock`, and an alias or static-subnet option may behave differently there than on Docker. If an integration test fails only on Podman, record it and verify on Docker (CI). Do not weaken the test.

## Out of Scope

- **Matching Jumppad's Docker plugin feature for feature.** This plan adds no volumes, health checks, image builds, port mappings or ranges, sidecars, registry authentication, or refresh and change detection. The Docker plugin does just enough with networks and containers to be useful and testable. (Spec non-goal.)
- **Docs drift the examples did not cause.** The rest of docs issue #4 stays with that issue. That includes the README's state-masking snippet and generic postgres illustrations elsewhere in the README and on the website. The state-masking page's call to action belongs to the configuration-example spec.
- **Modules and state encryption in the plugin example.** The rewritten example shows neither. Modules are documented in the README and covered by the e2e fixtures. State masking has its own docs.
- **The configuration-only example and prettylog.** These belong to the sibling specs `20261006112023-aadf3c10-configuration-example` and `20261006112108-17623cda-encoder-syntax-highlighting`.
- **The e2e suite and the example module layout.** The e2e plan `20261006071142-506b8289` owns both, including the README "Running them" paragraph. This plan relies on them and leaves them unchanged.
- **The older `plugins/example` (PersonPlugin) example.** It is untouched.
- **An automated website snippet check.** Matching snippets is a manual review. A cross-repo checker would be a separate piece of work.
