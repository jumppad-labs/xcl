# Language reference: XCL described page by page, with Go and Python side by side

xcl.dev now has a language reference, eight pages under `/language/` that describe XCL itself rather than one feature at a time, and every code example on the site that shows application code offers it in Go and Python through one tabbed code box whose choice is remembered across pages. The reference and the Python tabs were written against the language as released in xcl v0.3.0 and v0.4.0, and every example on the reference pages and every Python panel across the site was then tried against that release and corrected where the release behaves differently. The site navigation, the home page and the xcl README point to the reference, and the xcl CHANGELOG records it. The work spans the xcl-website repository and, for the README and CHANGELOG, the xcl repository.

## What was built

**The tabbed code box (xcl-website).** A new `CodeTabs` Astro component takes one fenced code block per language in named `go` and `python` slots, so Expressive Code still renders each block with its title and highlighting. The reader's language lives in one `localStorage` key, `xcl-lang`, applied as `data-lang` on `<html>` by an inline script in the page head before paint, so there is no flash of Go for a Python reader; CSS shows the matching panel in every box on the page, and a handler in the site shell switches the attribute, stores the choice, syncs `aria-selected` and handles arrow, Home and End keys following the WAI-ARIA tabs pattern. Blocked storage leaves switching working without memory. No dependency was added.

**Python beside Go on every existing page (xcl-website).** Every Go application-code box on the registries, GitHub registry, events, sensitive values, state masking, configuration text, diff, home and configuration-only example pages became a tabbed box with a Python panel written against the released `xcl-lang` package: `@xcl.entity` dataclasses, `xcl.LocalRegistry` and `xcl.GitHubRegistry`, `xcl.Config` with its options, the `xcl.*Error` exceptions, `xcl.Sensitive`, masks, saved-entity encoding, diffs and a `logging`-based event handler. Where Python has no form of a Go capability (a custom registry, a custom masker, `EncodeEntity`, `IncludeComputed`, `ShowReferences`, editor themes, a custom highlight renderer, diff rendering, in-process plugin registration), the Python panel says it is not yet available from Python, names what Python offers and links the xcl-python parity list. The four plugin authoring pages (plugin template, plugin example, replacement, plugin logging) each open with a statement that plugins are written in Go for now and work from Go and Python applications; their plugin and provider code stays Go-only, and their application boxes, including the twelve `xcl-docker` program boxes, gained Python panels. The site links config gained the xcl-python repository, parity list and PyPI URLs.

**The language reference (xcl-website).** Eight pages: the overview (what XCL is, the `.xcl` and `.vars` files it reads, the page list); entities (blocks and labels with `database "postgres" "main"` and `app "web"`, addresses, the built-in fields `depends_on`, `disabled` and `meta.*`, the built-in entity types); attributes and blocks (required and optional attributes, nested blocks, lists of blocks, named blocks collected by name, map attributes, object values, computed fields, sensitive fields and the entity base, each as XCL beside a tabbed Go struct with tags and a Python dataclass); references (another entity's attribute, a whole entity, a named block, processing order, `depends_on`, the module boundary); expressions (strings with references, lists, maps, conditionals, both `for` forms, splat, indexing, operators, and templating: `%{ }` directives are rejected and functions do the job); variables and outputs (defaults, a default built from another value, overrides from the application, `.vars` files and `XCL_VAR_<name>`, their precedence, outputs and reading them from the application); modules (using one, reading its outputs, the boundary, finding an entity inside it by full address, and sources: a local directory works, git, GitHub and HTTP do not yet); and functions (all 57 built-ins grouped and each with a runnable example, application functions in Go and Python, plugin functions, when calls run, and how name clashes are reported). Every page calls blocks entities and never says "superset", "interpolation" or "Terraform".

**Reachability (xcl-website and xcl).** The navigation gained a "Language" dropdown between "Features" and "Examples" listing the eight pages. The home page links the reference from "What is XCL?" with a "Learn the language →" button, from a new "Documentation" section after "Two examples" that the Go and Python guides will join, and from the variables, modules and functions feature cards; its hero badge reads "v0.4.0 · Go and Python" and the tagline ends "Available for Go and Python." The xcl README's Documentation list starts with the language reference, and the xcl CHANGELOG gained the spec's entry with **Breaking:** None.

**Verification against the release.** Every XCL and Go example on the reference pages was run with throwaway Go programs against `github.com/jumppad-labs/xcl v0.4.0` from the module proxy, and every Python panel on the site against the same release's engine built from the tagged commit with the xcl-python checkout, with the Docker example plugin v0.2.0 for plugin-dependent examples, running against a real Docker engine. Corrections made: a path with another extension is read as empty rather than rejected; the duplicate-name error is quoted with its real separator and range; a reference cycle is not caught by `Validate` and fails at `Apply`; the three set functions' results are sorted into lists, and a set published as it is through an `output` is marked not yet supported; a root output cannot be read as `output.<name>` from another block; a bad GitHub plugin repository or version aborts the Python process rather than raising; and the plugin example's Python `inspect.py` is named `inspect_entity.py` because a module of that name shadows the standard library. The built-in list matches the release exactly.

## Why it matters

Until now xcl.dev explained features one at a time and every example was Go. Someone writing configuration had nowhere to learn the language as a whole, someone mapping configuration onto their application's types had to infer the rules from examples, and a Python developer met Go on every page. The reference gives each question a section with a stable link, puts the Go struct and the Python dataclass beside each shape of configuration, and the tabs let a reader pick their language once and keep it. It also records exactly what the v0.4.0 release does, marking what is not yet supported, so the pages are a reliable description rather than a plan.

## Deviations from the plan

- Python examples were verified against the tagged source (libxcl built from the xcl worktree at v0.4.0, commit 93e1904, with the xcl-python checkout at 81673e5) rather than a PyPI wheel, by the orchestrator's decision: `xcl-lang` 0.4.0 is not on PyPI because the xcl-python release run failed, and the first published Python release will follow later specs. The pages keep `pip install xcl-lang`. The session running the last Python pass was cut off before reporting, so a later session re-ran that pass against the current page text.
- The PyPI project is `xcl-lang` (imported as `xcl`), not `xcl` as the plan wrote; the site links `https://pypi.org/project/xcl-lang/`.
- No test files were written for any site task, following the plan's Testing Approach and the website convention; the gates were `npx astro check` and `npm run build`, and tab behaviour, reachability, coverage, terminology and the plugin-page statement are manual items in the test plan.
- The "Using XCL with Go" and "Using XCL with Python" guides from the sibling spec had not landed, so Python-guide references link the xcl-python README for now, and the home page's "Documentation" section lists only the reference.
- `xcl.Find[*App]` on the entities page was corrected to `xcl.Find[App]` because `Find[T]` takes the struct type; the pre-existing `xcl.Find[*Postgres]` fence on the configuration text page is reported as a gap, not changed.
- Library and package gaps found and reported rather than fixed: `Validate` accepts a reference cycle and `Apply` fails with a raw dependency-graph error naming no entity; a set published through an `output` reads back as its cty `GoString`; a root-level `output.<name>` reference passes `Validate` and fails at `Apply`; an entity type with no fields beyond `types.ResourceBase` is never added to the evaluation context; `EncodeEntity` prints an unnamed list-block element as `volume "" { }`; in Python a bad GitHub plugin repository or version aborts the process (an unrecovered panic in `registry.(*GitHub).RegisterPlugin`), environment variables set at runtime are invisible to the in-process engine, an omitted `default=None` object attribute hydrates as the zero object and an omitted `Sensitive | None` field as a redacted `Sensitive`, an entity class used as a field type is rejected only at `xcl.Config(...)`, a non-dataclass base between `xcl.Resource` and the registered class silently drops its fields, `TypeNameClashError.details` names the synthesised Go struct, and `PluginNotFoundError` and `PluginVerificationError` are not subclasses of `PluginLoadError`.
