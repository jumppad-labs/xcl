# Changelog: config-decode — fill an application struct with one Decode call

## What was built

Applications that use xcl for configuration can now hand it a struct of their own and have it filled in one call, `c.Decode(&cfg)` or `xcl.Decode(c, &cfg)`. Fields are matched by type alone, with no struct tags:

- A `[]*T` field, where `T` is a registered type, receives every entity of `T`, exactly as `xcl.All[T]` returns them. That means declaration order, disabled entities included, and the configuration's own instances rather than copies.
- A `*T` field receives the single entity of `T`. It is set to `nil` when none is declared, and when more than one is declared the call fails with the same `*NotUniqueError` that `FindOne` returns.
- Every other field is left untouched: plain values, unregistered or plugin-provided types, and nested structs.

A target that is not a non-nil pointer to a struct returns the new `xcl.ErrInvalidDecodeTarget`, whose `*xcl.InvalidDecodeTargetError` detail names what was passed. On any error nothing is assigned. `Decode` is not generic, so its method form works on Go 1.25 as well as 1.27.

Building it involved four further changes in the library:
- **One shared lookup core.** The lookups (`Find`, `FindByType`, `FindOne`, `All`, `As`) were first moved onto a non-generic core over `reflect.Type`, and `Decode` uses that same core. As a result `Decode` and `All` cannot disagree. The whole existing test suite passed unchanged after the refactor.
- **Reference coverage.** New tests prove that a nested block referencing a registered bare-keyword block as a whole arrives filled in, through both a pointer field and a value field.
- **Example.** The config-only example now gathers its configuration with one `Decode` call, prints byte-identical output, and has AST guards that forbid going back to per-type lookups.
- **Documentation.** The README and CHANGELOG document `Decode`, and the docs site's configuration-only page shows the struct and the call.

## Why it matters

Previously an application asked for each kind of block separately and assembled its own structure by hand. Now one call fills it, and reading a new block type is a matter of adding a field.

## Deviations from the plan

- **Declaration order was not real, and was fixed in the parser.** The parser kept parsed entities in a map and built the state by ranging over it, so `c.Entities()` and every lookup came back in random order. The planning spike had passed by chance. With the user's agreement (they expect ordering to matter for a future diff feature), the parser now records first-seen declaration order and builds the state from it. Lookups, `c.Entities()` and saved state now follow declaration order deterministically.
- **The README's worked example leaves out a single `*Server` field**, because its two servers would make the call fail. The not-unique outcome is described in prose instead.
- **The example's `printRouting`** reports a missing service or ingress itself rather than through `Find`'s not-found error.
- **The docs site page's sample output** was reordered to match the now-deterministic real output. The site's dependencies had to be installed (`npm ci`) before `astro check` would run.
