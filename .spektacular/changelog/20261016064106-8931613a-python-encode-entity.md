# Python programs encode the entities they hold as configuration text

## What was built

Python programs that embed xcl can now turn any entity they hold into xcl configuration text, the same text Go's `xcl.EncodeEntity` writes for it. The entity can come from a lookup or an event, be an instance of a registered dataclass built by hand, or be the generic `xcl.Entity` of a plugin type. The call takes Go's four encoding choices plus terminal highlighting, and the existing saved-record call gains the same choices. xcl's shared engine renders the text, so the parity suite can prove the Python text is byte-identical to Go's for every fixture and every combination of choices.

- **xcl (released as v0.11.0):**
  - The core service gains `EncodeEntity`, a lookup that renders an entity's JSON record in the shape a lookup returns it, possibly edited or built by hand. It takes `highlight` and an `EncodeOptions` message: include computed, include empty, reveal sensitive, show references.
  - `EncodeSavedEntity` takes the same `options`, and a call that sends none renders exactly as before.
  - Both colour after rendering and are refused with `operation_in_progress` while an operation runs.
  - Go gains `Config.EncodeEntityRecord(data, options...)`, which renders such a record through the path `EncodeEntity` uses.
  - A lookup's JSON loses two things: it writes the marker for every sensitive field, set or not, and it leaves out empty lists and maps. Both are filled from the Config's own copy of the entity that `meta.id` names, so the text is what Go writes for that entity. Without reveal the marker is still written, and an unset secret is left out.
  - The bindings' parity program records an `encode` section: for every non-builtin entity of every fixture, the looked-up and saved texts under all 16 combinations, plus hand-built texts for the addresses a fixture lists. A new `encode` fixture covers subtypes, secrets, references, sensitive bare references and templates, and every empty form.
- **xcl-python:**
  - `Config.encode_entity` and `xcl.aio.Config.encode_entity` take `include_computed`, `include_empty`, `reveal_sensitive`, `show_references` and `highlight`, all off by default, and `encode_saved_entity` takes the same keywords.
  - `record_of`, the mirror of hydration, turns an instance into the record the engine reads. A hydrated instance remembers the JSON it came from, so fields left untouched are written exactly as the engine gave them, and only edits differ from Go.
  - Bad input raises the existing exceptions (`NotEncodableError`, `NotRegisteredError`, `OperationInProgressError`) before or from the engine.
  - The protocol messages are regenerated, the engine pin is `v0.11.0`, the parity runner writes the same `encode` section, and README and PARITY.md document the call.
- **xcl-website:** the configuration-text guide's Python tabs show the working calls for converting an entity, provider-filled values, empty attributes (a new section), secrets, references and highlighting, and the events page mentions encoding an event's entity.
- **Design:** the Lookups section of the shared-library design lists `EncodeEntity` and the saved-record options, and explains the fill.

## Why it matters

Python was the only language that could read configuration but not write an entity back as text, which is how programs show users what a configuration holds. Rendering in the shared engine, rather than in Python, means the two languages cannot drift, and the parity suite makes "the same text as Go" a release gate.

## Deviations from the plan

- **The engine fills from its own copy whenever `meta.id` matches, not only with reveal (approved by the user).** Real-engine tests showed that the lookup JSON writes the marker for unset secrets, so a looked-up entity's text showed `password = "(sensitive)"` where Go writes nothing.
- **The fill also restores empty lists and maps the lookup JSON left out.** Without it, a configured `tags = []` was dropped from the text.
- **Hydration remembers each instance's source JSON (approved by the user).** Rebuilding the record from the instance alone wrote dataclass defaults and hydrated `[]` and `{}` that Go does not have.
- **The spec's empty-fields criterion was amended (approved by the user).** Go writes a list the configuration sets to `[]` even without include-empty, so the criterion now speaks of a list left unset.
- **The parity fixture declares its unset map nullable.** A hand-built instance can only spell an unset map as `None`.
- **Delivery.** xcl was merged with `breaks-bindings`, so xcl-python pinned `v0.11.0` itself rather than through the automatic engine bump. The worktrees were merged before the release so the PR could be opened.
