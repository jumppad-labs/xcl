# Replacement and dependency changes

## What was built

Plugins can now answer that a resource is unchanged, needs an update in place, or must be replaced. Each resource is also told which of its dependencies the same apply will update or replace, so it can decide its own outcome.

**The contract (xclconfig).**
- A new public `entity` package holds `entity.Change` (`NoChange`, `Update`, `Replace`) and `entity.DependencyChange{Address, Change}`.
- `ResourceProvider[T].Changed` is now `Changed(ctx, old, new, dependencies []entity.DependencyChange) (entity.Change, error)`. The adapter, the in-process and gRPC hosts, the gRPC server and the testing helpers carry the same signature.
- The plugin protocol gained a `Change` enum, a `DependencyChange` message, `ChangedRequest.dependencies` and `ChangedResponse.change`; the old `bool changed` field is reserved. An unknown change value is an error on either side, so a mismatched plugin fails loudly.
- `DefaultChanged` answers update or no change and ignores dependencies.

**Decide, then act (xclconfig).**
- Plans and applies share one decide pass, walked in dependency order:
  - a new resource is created;
  - a resource saved `failed` or `destroy_failed` is replaced;
  - every other saved resource is read and asked `Changed`, together with the provider-backed dependencies the record says will update or replace.
- Outputs, variables, modules and config-only types are looked through to the resources behind them.
- A resource whose inputs are only known after the apply is read with its saved values and is planned as at least an update.
- Any failure while deciding stops the apply before anything changes, and nothing is saved.
- Apply then acts on the decisions:
  1. It destroys every replaced and removed resource, dependents first, saving state after each.
  2. It creates new and replaced resources, updates updated ones and keeps unchanged ones, in dependency order.
- A failed destroy saves `destroy_failed` and stops the apply. A failed create saves `failed`. Either way the resource is replaced again next time.
- The old in-walk rebuild is gone. Every read and changed check now happens before the first destroy, create or update.

**Plans say why (xclconfig).**
- `diff.Resource` gains `Reason` (`failed`, `provider` or `dependency`) and `ReplacedDeps`, both in its JSON form.
- The rendered comment line names the cause, for example `# docker.container.web will be replaced because docker.network.app is replaced`.

**Plugins and examples (xclconfig).**
- The plugin example's Docker network replaces on a subnet change. Its container replaces on image, command, environment or network changes, or when its network is replaced. Its template replaces on a destination change.
- The person plugin replaces on a name change. The e2e fixtures gained two replace rules.
- The example's second configuration moved to `example/plugin/config-subnet/` with a `make replace` target, so `./config` applies on its own again.
- Against real Docker, applying it rebuilds the network on `10.42.0.0/23` with a new container and a re-rendered template, and the next plan reports no changes.

**Tests (xclconfig).**
- New tests cover every layer: the contract, the decision record and dependency resolver, the decide and act passes, provider rules, reason rendering, and Docker-gated example tests.
- An exact plan-equals-apply comparison runs for every e2e scenario, and the same change is checked through in-process and external plugins.

**Documentation (xclconfig and xcl-website).**
- The project guides, README and CHANGELOG describe the new answer, the dependency list, decide-then-act and the breaking changes.
- The website gained a "Unchanged, update or replace" guide, linked from the Guides menu.
- The diff page now explains the three replacement reasons.
- The plugin example page walks through the subnet change in place of the misleading image-bump "update" walkthrough.

## Why it matters

Before this change, a change a resource could not take in place, such as moving the plugin example's Docker network to a new address range, was recorded in state while the real network stayed as it was. The container attached to that network was never told.

Plugin authors can now express the changes their resources can't make in place, and react to replaced dependencies. Anyone applying a configuration gets real infrastructure that matches what they wrote, in a safe order. The plan shown beforehand lists exactly what the apply will do, and says why each replacement happens.

## Deviations from the plan

- **Two parses per apply.** `Apply` parses the configuration twice, once for the decide pass and once for the act walk, so decide-pass placeholders and read values never reach a provider. The second parse emits no events. A test caught the duplicate parse events this first produced.
- **Failed decide returns no state.** A failed decide pass, or a cancelled context, returns no state rather than the previous state, so the saved state is untouched.
- **Debug logging.** The decide pass logs its counts and each replacement's reason at debug level. Event tests that assert exact streams now ignore those core log events, and one delivery count grew by one.
- **Recorder name.** The diff recorder kept its name `diffRecorder`, and `diff.ReplaceReason` landed with the decision record, ahead of the diff task. The plan allowed both.
- **Module look-through.** A resource inside a module is told about every changing resource the module block's `variables` reference, not only the ones it reads, because variable entities carry no links.
- **Dependency-driven replacement in e2e.** No e2e fixture provider replaces because a dependency is replaced. That case is covered by the parser tests and by the Docker example; the e2e dependent scenario covers the unknown-input floor instead.
- **Subset helper removed.** The old subset plan-versus-apply helper was removed because exact equality now holds for every scenario.
- **The config move.** It was done with `mv`, not `git mv`, so nothing is staged.
- **Extra test.** `TestSubnetChangeRemovesTheOldNetwork` was added beyond the plan.
- **Extra documentation.** `docs/overview.md` was corrected as well.
- **Diff page addresses.** The website diff page's sample uses `resource.*` addresses, to match the rest of that sample.
- **Left as found.** Existing `#L<line>` source links in two core docs were left unchanged and may point at the wrong lines. The website plugin page's existing load-event samples don't show the `registry=local` field that load events now carry.
