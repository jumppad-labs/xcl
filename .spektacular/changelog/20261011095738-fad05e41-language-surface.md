# Language surface: XCL becomes a language with a settled shape

Released as xcl v0.3.0 (tag `v0.3.0` on commit `6cdf936`), with the plugin template, the example Docker plugin, the website and the VS Code extension brought into line.

## What was built

**Variables, references, optional fields and templating (xcl).** A variable is overridden from the environment with `XCL_VAR_<name>` and nothing else in the environment becomes a variable: `Config` builds every operation's parser options through one helper that sets the prefix, an empty prefix reads nothing, and a value containing `=` is kept whole. Dependency links are extracted with the parser's own variable walker, so a reference is found inside a `for` expression, an index expression, parentheses and a relative traversal, and a `for` expression's key and value names are never references; a variable's default built from another entity resolves in dependency order. An object or map value written as an attribute may leave out the fields the Go type tags `optional`, through a new `gocty.ImpliedConstraintType` that `gohcl.DecodeExpression` converts against, with a null optional field left at its zero value. The forked template parser rejects every `%{ … }` directive at the directive, with an error pointing to `format`, `join`, `template_file` and conditionals inside `${ }`; interpolation and the `%%{` escape are unchanged.

**Named child blocks (xcl).** `hcl.BlockHeaderSchema` gained `LabelsOptional`; a `map[string]T` block field, and a slice field whose element has at most one label field, take one optional name label. Blocks are collected into the map by name, with the element's label field set from the key; a list accepts named and unnamed blocks and keeps the name when the element has a field for it. A block without a name where a map needs one, and a repeated name in a map or list, are reported at the block, by `Validate` (through `CheckBody`) and by `Apply`. Links, diff paths, the configured-value check, the validate and sensitive problem paths and the encoder's reference lookup address map blocks by name (`listener["https"].port`), so `app.web.listener.https.port` and `for name, l in app.web.listener` work and a map of blocks is written back with each block's name. Every panic the decoder could raise on a Go type is a positioned "Unsupported decode target" diagnostic, and a new `gohcl.ValidateSchemaType`, run by the catalog at declaration and at plugin load, reports a bad Go type as an `InvalidTypeError` from `NewConfig` or from the first operation.

**Functions from applications and plugins (xcl).** `registry.Registry` gained `Functions()`, `registry.Local.RegisterFunction(name, fn)` sits beside `RegisterType`, and the GitHub registry delegates. The catalog owns the function set: it checks each name against the builtins and the functions already held, converts the Go func through a shared `GoFuncSignature`/`GoFunc` in `internal/functions` (string, bool, every number kind, and slices and string-keyed maps of those, converted through gocty), and hands the set to the parser, which merges it with the builtins and keeps the sensitive-value redaction wrapper. `plugins.ProviderFunction` is reshaped around a language-neutral `FunctionSignature` and a JSON `Call`; `plugins.NewFunction` builds one from a Go func and `plugins.NewFunctions` backs a provider's `Functions()`; `PluginBase` collects each provider's functions, refusing a name two providers of one plugin both offer; `PluginEntityProvider` and `PluginHost` gained `GetFunctions` and `CallFunction`, served by the direct host and, over the additive `GetFunctions`/`CallFunction` RPCs on protocol version 1, by the gRPC server and host, with `Unimplemented` read as "no functions". When a plugin loads, the catalog checks its function names against builtins, application functions and loaded plugins and builds a configuration function from each signature whose calls marshal arguments as a cty JSON array, call the host and unmarshal the result. Clashes are `FunctionNameClashError`s naming both sources and registries: from `NewConfig` for application functions, and from the first operation for anything involving a plugin. `ParserOptions.CustomFunctions` is removed. Two compiled fixture plugins support the tests.

**Docs and changelog (xcl).** The plugin developer guide describes `Functions` as offering functions to configuration and gained an "Offering a function" section; `docs/plugins.md` gained "Application functions" and shows `RegisterFunction` beside `RegisterType`; `docs/overview.md`, `docs/README.md` and the README mention functions from applications and plugins; `CHANGELOG.md` gained the entry for this spec with every breaking change.

**Plugin template.** Moved to xcl v0.3.0. The note provider offers `note_filename(title)`, built once in `NewNoteProvider` with `plugins.NewFunction` and returned from `Functions`, still the last method; the sample names its note `note_filename("Greeting")`; the README gained an "Add a function" section; unit and end-to-end tests cover the function in process and as a separate program.

**Docker plugin.** Moved to xcl v0.3.0 with no source change; its providers offer no functions. Build, lint, unit, real-engine and end-to-end tests pass.

**Website.** The landing page names `XCL_VAR_<name>` and says "57 built in" plus functions from applications and plugins; the example pages' comments use `XCL_VAR_`; the plugin template page says a provider's `Functions` offers functions to configuration. No page was removed.

**VS Code extension.** The grammar needed no change; the tokenize fixture and test pin that `%{ … }` in quoted strings and heredocs is plain string text while `${ … }` keeps its interpolation scopes, and the changelog records it.

## Why it matters

XCL exposed everything its HCL-derived parser happened to support, and in several places did not do what its documentation said: environment overrides did nothing, applications had no way to add functions, plugins could not offer them, and named child blocks could not be collected by name. The language now has a settled shape, a declarative language that keeps references, expressions and functions, drops string templating from the core, and collects named child blocks by name, and the library matches it, so the language reference can describe real behaviour. Configuration authors get `XCL_VAR_`, named blocks and working `for` references; developers embedding XCL register functions the way they register types; plugin authors offer functions from a provider by following the template.

## Deviations from the plan

- The optional-attribute constraint builder lives in `gocty` (`ImpliedConstraintType`) rather than a new `gohcl/types.go` helper, since gocty already owns wrapper handling and embedded-struct flattening.
- The JSON body (`internal/xcl/json`) was changed after all: for an optional-label block type a JSON array holds unnamed blocks and a JSON object named ones, so the fork's own JSON-bodied gohcl tests stay meaningful. XCL never reads JSON configuration.
- `CheckBody` gained the missing-name and duplicate-name checks, so `Validate` reports them at the block, meeting the spec's "fails validation" wording that the decoder alone met only at apply.
- `InvalidTypeError` carries a `Provider` beside `Type`, `Registry` and `Err`; the exported `ImpliedBodySchema` and `getFieldTags` keep panicking as wrappers for validated types; `any` attribute fields are accepted because gocty treats the empty interface as dynamic.
- `Config.Diff` leaves provider-less registered entities out, so the "change to one named block" criterion is proven by `resourceChanges` over two real applies in the parser package rather than through `Config.Diff`.
- Links address single nested blocks by position (`network[0].name`) while validate and sensitive problem paths index lists only; both conventions were kept. The configured-value warning renders map keys bare (`listener[https].port`), as it always did for attribute maps.
- Directive upstream table cases were removed and replaced by a non-table test file; the `templateParser`'s if/for code stays but is unreachable; the root Validate test asserts on the diagnostic Detail, since `ParserError.Message` never carries a Summary.
- `GoFuncSignature` names parameters `arg0..n`, rejects variadic funcs, and accepts nested slices and maps of primitives. A `NewFunction`-built function does not receive the call context, so a provider that needs to log or observe cancellation implements `ProviderFunction` itself. A variadic plugin signature is refused at load.
- No binary built against the pre-functions protocol exists, so the old-plugin case is proven with an `Unimplemented` loopback client and, end to end, with a plugin offering no functions.
- The template's function appends `.txt`, keeping the sample's `greeting.txt` assertions; a func of the wrong shape panics through `mustFunction` when the provider is built rather than changing `NewNoteProvider`'s signature.
- The release tag was cut by the orchestrator on the spec branch's commit `6cdf936`; moving v0.3.0 into the plugin repos pulled in `github.com/ProtonMail/go-crypto` and `github.com/cloudflare/circl` as indirect dependencies.
