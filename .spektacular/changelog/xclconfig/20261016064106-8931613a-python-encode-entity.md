# Render any entity record as configuration text from the core service

A host in another language can now turn any entity it holds into xcl configuration text with the same choices Go offers: include provider-filled fields, include empty fields, reveal sensitive values and show references as written, plus terminal colouring. The saved-record call takes the same choices, and calls that pass none behave exactly as before. Go programs get the same capability for a JSON entity record as a new `Config` method. The text is identical to what `xcl.EncodeEntity` writes for the entity, and it ships in v0.11.0.

> Derived from project xcl (jumppad-labs), spec/plan 20261016064106-8931613a-python-encode-entity. See the project-level record for the full feature.

## What changed in this repo

- **Protocol.** `proto/xcl/core/v1/core.proto` gains `EncodeOptions` (`include_computed`, `include_empty`, `reveal_sensitive`, `show_references`), `options = 3` on `EncodeSavedEntityRequest`, and `rpc EncodeEntity(EncodeEntityRequest) returns (EncodeEntityResponse)`. Fields are only appended, and `coreservice/proto/core.pb.go` is regenerated.
- **Record encoder.** `encode_record.go` adds `(*Config).EncodeEntityRecord(data, options...)`. It decodes the record with display semantics and renders it through the shared `encodeEntity`. Before rendering, it fills from the Config's own entity named by `meta.id` what a lookup's JSON loses: sensitive values holding the marker, and empty lists and maps the JSON left out. A value the record holds is never replaced.
- **Core service.** `coreservice/lookups.go` adds the `EncodeEntity` handler and passes the options through `EncodeSavedEntity`. The two handlers share the refusal while an operation runs, the empty-record check, the options translation and the colouring. `coreservice/service.go` registers the handler.
- **Parity.** `bindings/libxcl/cmd/parity` records an `encode` section for every fixture: looked-up, saved and, for addresses in `hand_built.json`, hand-built texts under all 16 combinations. A new `testdata/parity/encode` fixture and the fixtures README cover it.
- **Tests.** Root-package tests for `EncodeEntityRecord` cover:
  - equality with `EncodeEntity` for each choice;
  - reveal, edits, missing and unknown ids;
  - nested, list and map fills;
  - unset secrets and configured empty lists;
  - errors.

  `coreservice` tests cover both calls with every choice, highlight, errors and refusal during an operation. Parity program tests cover the new section.
- **CHANGELOG.md** has the spec's entry, with `**Breaking:** None.`

## Why

Rendering stays in the engine so every language binding writes Go's text. The core service may only reach the engine through public API, so the fill sits in a new public `Config` method rather than in `coreservice`, and Go's own encoder and its options are unchanged.
