# The engine for other languages: context-taking operations, untyped lookups, schema v1, the core service and libxcl

xcl's engine can now be driven from a language other than Go. Every operation has a form that takes a context and stops when it is cancelled, entities can be looked up by type without a Go type, a block type can be declared from a language-neutral schema, and the whole of the library is offered through one message-based core service that a new shared library, libxcl, exposes through four C functions. Tagging a release builds libxcl for eight platforms, attaches the signed archives to the release and triggers the Python package's release. Go programs keep the API they had, with no cgo anywhere in the library.

## What changed in this repo

- `ValidateContext`, `ApplyContext`, `DiffContext`, `DestroyContext` and `LoadContext` on `Config`; the existing methods call them with a background context. A cancelled context starts no further provider call, saves the progress made and returns an error wrapping `context.Canceled`; the parser now appends the cancellation beside any other error of a cancelled walk (`config.go`, `config_diff.go`, `internal/parser/parser.go`, `internal/parser/destroy.go`).
- `Config.FindEntitiesByType` and `Config.FindOneEntity`, untyped lookups sharing the segment rules and errors of `FindByType` and `FindOne` (`query.go`, `query_untyped.go`).
- Schema v1 reader in `internal/schema/v1.go`, routed by `CreateInstanceFromSchema` when a document carries `schema_version: 1`, and `registry.TypeFromSchema` (`registry/schema.go`). Plugins keep sending the legacy schema.
- Two fixes Go users see: `Config.addressParser` publishes its cache atomically, ending a race between concurrent lookups; an entity's `meta.links` are recorded in the order they were written.
- The CoreService protocol in `proto/xcl/core/v1/core.proto` with buf configuration (`proto/buf.yaml`, `buf.work.yaml`, `buf.gen.yaml`), `make core-protos`, `buf lint` and `buf breaking` in CI, generated into `coreservice/proto`.
- The `coreservice` package: `Service.Call` and `Release` with the six statuses, the handler table held to the descriptor, `CreateConfig` mapping every option and registry (schema-declared types, external plugins, plugin directories, GitHub registries, state path or host store, masks, events, variables, host functions built by reflection), the task queue, operations with cancellation, the event and host-state-store bridges, the lookups and the error mapper.
- `bindings/libxcl`, a nested cgo module exporting `xcl_abi_version`, `xcl_call`, `xcl_free` and `xcl_release`, with `xcl.h`, a smoke test through the ABI, `make libxcl` and `make test-libxcl`, a CI job, and `.github/workflows/libxcl-release.yml` building, packaging, signing and publishing eight archives on a tag and dispatching xcl-python.
- Fixture plugins `slow` and `recording`, seven parity fixtures and the Go parity program under `bindings/libxcl/testdata` and `bindings/libxcl/cmd/parity`.
- The CHANGELOG entry for this release and a README note pointing to the Python package.

## Why

The epic makes XCL a language with more than one implementation, and the first is Python. Rather than reimplementing the parser, graph, lifecycle, change detection, sensitive handling, state and events, the Go engine is compiled once and driven through one protocol, which needed the root module to expose a few things it only held privately: cancellation from a caller, lookups without a Go type, and a type declared from a description any language can write. Everything added is public, additive and documented, and the cgo-free guard keeps the library as it was for Go users.
