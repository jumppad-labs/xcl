# Python support: XCL runs from Python through one shared engine

XCL, which existed only as a Go library, now runs from Python. The Go engine is built once as a C shared library, libxcl, and driven through one message-based core service; a new Python package, published as `xcl-lang` and imported as `xcl`, bundles that engine in each platform's wheel and offers a synchronous and an asyncio API over one poll loop. The work spans the xcl repository and the new xcl-python repository. The release was cut as xcl v0.4.0: the signing key, passphrase and dispatch token secrets were added to xcl, a PyPI pending publisher was set up for `xcl-lang` with the `pypi` environment on xcl-python, both branches were merged (xcl `93e1904`, xcl-python `81673e5`) and the orchestrator tagged `v0.4.0` on `93e1904`; the libxcl release workflow run 38172909823 builds, signs and publishes the engine and dispatches the Python package's release, which confirms the release-time acceptance criteria left open in the plan.

## What was built

**The Go library (xcl).** Every operation gained a context-taking form, `ValidateContext`, `ApplyContext`, `DiffContext`, `DestroyContext` and `LoadContext`; the existing methods pass a background context. Cancelling the context starts no further provider call, saves the progress made and returns an error wrapping `context.Canceled`, which the parser now always reports beside any other error of a cancelled walk. `Config` gained `FindEntitiesByType` and `FindOneEntity`, untyped lookups by type segments sharing the rules and errors of `FindByType` and `FindOne`. Schema v1, a language-neutral JSON description of a block type covering attributes, nested blocks, lists of blocks, maps of named blocks with their optional name label, and optional, defaulted, sensitive and computed fields, is read by `internal/schema` beside the legacy plugin schema, and `registry.TypeFromSchema` declares a type from it. Three latent problems in the root module were fixed on the way: a data race in the lazily cached address parser, `meta.links` recorded in Go's random map order, and a cancellation hidden behind other errors.

**The core service (xcl).** `proto/xcl/core/v1/core.proto` defines the CoreService protocol, generated and checked with buf. The `coreservice` package, built without cgo, dispatches every method by name through `Service.Call(handle, method, request)` with the design's six statuses; `CreateConfig` maps every configuration option and both registry kinds, with schema-declared types and host-language functions built by reflection from a declared signature so they behave exactly as Go application functions; the lookups return entities as JSON with sensitive values as the marker; every error crosses with a stable code, its details and positioned causes. Operations run on a goroutine under a cancellable context and post their events, state-store calls, function calls and end as one ordered stream of tasks the host polls and completes, so a host may implement the state store and offer functions.

**The shared library (xcl).** The nested cgo module `bindings/libxcl` exports `xcl_abi_version`, `xcl_call`, `xcl_free` and `xcl_release`; `make libxcl` builds it stamped with a version, CI builds, checks its exports and smoke-tests it through the ABI, and the root module's cgo-free builds stay the guard. A release workflow builds it for Linux x86-64 and arm64 (glibc 2.28 and musl), macOS x86-64 and arm64 and Windows x86-64 and arm64 on a tag, attaches signed `libxcl_<version>_<os>_<arch>` archives to the GitHub release and dispatches the xcl-python release. Fixture plugins (`slow`, `recording`), seven parity fixtures and a Go parity program let any binding be compared with the Go API record for record.

**The Python package (xcl-python).** The transport loads libxcl lazily through cffi in ABI mode with ctypes as the fallback, releases the GIL during calls, checks the ABI and engine versions, and refuses use in a child forked after the engine was loaded with an error naming the `spawn` start method and creating the configuration after the fork. A descriptor-built client maps every engine error to an exception class under `xcl.Error`. Entity types are dataclasses decorated with `@xcl.entity(type, subtype)`, whose annotations (optional, defaults, `Sensitive`, `Computed`, nested blocks, lists of blocks, dicts of named blocks) derive the schema v1 document and into which entity JSON hydrates, with `xcl.Entity` for unregistered types. `xcl.Config` takes every option and runs validate, diff, apply, load and destroy, with lookups, outputs, diffs, events, custom state stores, masks, variables, Python functions, and Go plugins from a path, a directory or the GitHub registry with signature verification. `xcl.aio.Config` offers the same surface as awaitables that never block the loop, with async functions, handlers and stores, and cancellation that stops the engine's work. The Go–Python parity suite gives identical records on every fixture. CI tests the eight platforms against CPython 3.10 through the latest release; the release workflow verifies the signed engine archives, builds eight `py3-none-<platform>` wheels and an sdist, publishes with Trusted Publishing and installs the published package on every platform. The README, `PARITY.md` and docstrings on every public name document it.

## Why it matters

Python developers could not use XCL at all. They now get the same engine Go programs use, not a reimplementation: the parser, graph, lifecycle, change detection, sensitive handling, state and events run unchanged, so a Python program gets the same validation errors, diffs, entities, outputs and state as a Go program, uses the same plugins, and adds its own functions. It serves people building command-line and Jumppad-style tools in Python and teams running asynchronous services, and it is the first implementation beyond Go of a language the rest of the epic documents for more than one implementation. Go users gain context-taking operations and untyped lookups and are otherwise unaffected.

## Deviations from the plan

- The distribution is `xcl-lang`, not `xcl`: the name on PyPI belongs to another project. The spec's Requirements, Acceptance Criteria and Success Metrics were amended by the orchestrator; the import name stays `xcl`.
- Handles are the service's own never-reused `uint64` table rather than `runtime/cgo.Handle`, which does not link under `CGO_ENABLED=0`.
- Three root-module fixes beyond the planned additions: the address parser cache is published atomically (a real race between concurrent lookups), `meta.links` follow written order, and the parser always appends a cancellation beside a walk's other errors.
- `Validate` leaves missing required attributes to decoding, pre-existing behaviour for every type; the spec's "fails validation at the block's position" is met by the positioned error `apply` and `diff` report. A cancel is honoured between provider calls; a lifecycle call already running finishes first.
- Variadic host functions are refused with `invalid_function`, since the Go-func conversion rejects variadics. The published Docker plugin release used by the tests is v0.2.0, which protocol 1 loads unchanged.
- Messages are generated with protoc rather than buf's remote plugin; buf 1.27 locally reads only v1 config, so the proto module is `proto/buf.yaml` with a root `buf.work.yaml`, and CI pins buf 1.50.
- The release-workflow and CI/release tasks, the release task and the dry-run criterion of the secrets task are ticked with those acceptance criteria left unchecked: they describe runs on GitHub, confirmed by release run 38172909823 and the xcl-python release it dispatches (the manual dry run was skipped by the user's decision).
- Host functions, the libxcl smoke test, the asyncio module and several later tasks' files were written ahead of their workflow step while test agents ran; each was verified and ticked in its own step.
