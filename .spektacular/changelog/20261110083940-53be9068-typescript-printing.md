# TypeScript printing, themes and the pretty logger

## What was built

`xcl-lang`, the TypeScript package, now prints what xcl produces as Go and Python do, byte for byte:

- **Errors.** `printError` and `formatError` print a configuration mistake as Go's report: summary, location, numbered source lines with the fault marked, and detail wrapped at 80 columns, or at a chosen width, or not at all. Any other value prints its message or text form, so printing never throws. An `XclError` carries its report as labelled text (`tokens`) and as plain text (`report`). `console.error` shows the report, in colour when Node's console colours that stream. An uncaught error shows it as plain text, because the plain report is stitched into `stack` between the first line and the frames. `message` stays one line. pino's `err` serializer and winston's `format.errors()` carry `problems` and `report` with no configuration.
- **Entities and change summaries.** `config.printEntity` and `config.entityTokens` print an entity with Go's four encoding choices, and `printDiff` prints a change summary, whose labelled text is now on `diff.tokens`.
- **Formats and themes.** `plain`, `terminal`, `html`, `htmlInline` and `svg` are functions of one `Formatter` type, so a user's own format is accepted anywhere. Each is held to xcl's published reference outputs. Themes are plain objects of style strings, extended with a spread, with a kind falling back to its category, then plain text. `validateTheme` names every unknown word. `loadVSCodeTheme` has the engine convert a VS Code colour theme. `forStream` picks terminal colour for a terminal unless `NO_COLOR` is set.
- **Stylesheets.** `css(theme)` generates Go's stylesheet. The build writes the default as `dist/xcl.css`, exported as `xcl-lang/xcl.css`.
- **Logging.** `events.toLogger(logger)` writes each event to any logger with the four level methods, at Go's levels and messages, fields first (pino) or message first (winston).
- **Pretty logger.** `prettylog.handler()` writes each event as Go's example pretty logger does, from one line of setup:
  - each created entity's configuration, with values the provider filled in, beneath its line;
  - each configuration mistake's report beneath its error line, once per problem;
  - one line of guidance when entity data is off;
  - one warning per failed render, with variables, outputs and modules skipped.

  Each group goes out in one write and the logger never waits on the stream. It can write through an application's logger instead of a stream. `prettylog.levelFromEnv()` reads `XCL_LOG_LEVEL`.
- **Parity.** The parity suite now compares printed reports, printed entities, printed change summaries, logged events and pretty-log output with Go's for every fixture. Nothing is left out of the comparison.
- **Design.** In xcl, `printing-and-highlighting.md` now says that `console.error` uses custom inspection, while an uncaught error's report comes from `stack` as plain text, with no process listener.

## Why it matters

Before this, a TypeScript program saw a configuration mistake as one line, could not style xcl's output or render it for a web page or an image, and had to write its own event handling. Now a mistake shows the lines in question wherever it ends up: printed, as a string, on the console, uncaught, or in JSON logs. Output can be plain, coloured, HTML or SVG, and one line of setup shows what xcl is doing. This serves developers building tools on the TypeScript package and the people who read what those tools print.

## Deviations from the plan

- The design correction was applied by the orchestrator, after the user approved the wording this run proposed. The implement run does not write design documents.
- The core plan's xcl-source helper did not exist, so `test/helpers/xcl-source.ts` was added to find xcl's reference outputs.
- `loadVSCodeTheme` reaches the shared engine client through a new internal `sharedEngineClient` in `src/config.ts`.
- A diff's labelled text is read in `src/internal/poll.ts`, where the finished operation is, rather than in `src/config.ts`.
- `npm run test:unit` builds the package first, so the shipped stylesheet exists for its test. The Makefile changed only by a comment.
- A detail whose key matches one of Go's named log fields does not overwrite that field.
- In event lines, a whole number is written as an integer only within the safe integer range; beyond it, Go's float form is used. An event's error is written as its one-line message.
- The event's link to its configuration is set inside `ConfigImpl`, which wraps `onEvent`. Bad pretty-logger options throw `InvalidArgumentError`.
- The documentation's first goal check found six Go highlight items missing from the parity record. They were added.
- Both open questions resolved as planned. The uncaught route works on Node 22, 24 and 26 (run locally on 26 and in Podman on 22 and 24), and pino and winston both carry the `report` accessor.
