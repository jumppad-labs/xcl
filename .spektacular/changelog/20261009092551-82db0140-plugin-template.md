# Plugin template: the standard plugin layout as a GitHub template repository

## What was built

**xcl-plugin-template (new repository, `jumppad-labs/xcl-plugin-template`).** This is a GitHub template repository holding a complete xcl plugin built to the standard plugin layout. Its one resource, `notes "note"`, writes a note to a file, so it builds, tests and applies with nothing else running. It contains:

- **Backend client:** `client/files` is the plugin's only backend layer. It is a narrow `Files` interface over the local disk, with its own `Info` type, a local implementation, and tests against a temporary directory. Its strict Mockery double is generated into `client/files/mocks` by `make generate`.
- **Entity:** `entities/note.go` holds the block type alone. It has the configured `directory`, `name`, `content` and `mode`, and the computed `path` and `checksum`.
- **Provider:** `providers/note.go` is built through `NewNoteProvider(files.Files)`.
  - The settings that need a replace are one exported list, `ReplaceSettings` (`directory`, `name`).
  - `Changed` is explicit: it answers replace for those settings or for a replaced dependency, update for any other change, and otherwise defers to `DefaultChanged`.
  - `Update` acts only on the changes it is given. A content change rewrites the file, and a mode change on its own only changes the mode.
  - Unit tests against a fresh strict double cover every rule and error path.
- **Plugin type and program:** `notes.Plugin` is in the root package, and its `Init` builds the client once. `cmd/notes` serves the same type as a separate program.
- **Sample:** `examples/basic` is a sample configuration with a `directory` variable.
- **End-to-end tests:**
  - `e2e/` applies the sample, requires the next plan to report no changes and destroys it, once registered in-process and once as the built binary.
  - Further tests require a real plan to show a replace for a name change and an update for a content change.
  - `e2e/stateonly` imports only xcl, the registry and `entities`, and reads the applied note back from saved state into `entities.Note`.
- **Make targets:** `build`, `test`, `lint`, `generate`, `inprocess`, `external`, `dist` and `release`.
- **CI:** GitHub Actions run build, lint and test plus a snapshot `make dist` on every push and pull request, and the suite weekly against the latest xcl release.
- **Release workflow:** on a `v*` tag, it refuses to run without the signing key. It runs the tests, builds the six platform archives and the checksums with `make dist`, signs the checksums with gpg into an armoured detached `.sig`, and publishes with `gh`, in exactly the release asset contract the GitHub registry installs.
- **README:** it is task-ordered and covers starting, making the template yours, the layout, one command per task, the change decision, adding a resource, the signing key, releasing, installing and verifying releases.

**xcl.**
- `docs/plugin-layout.md` writes down the standard layout:
  - the tree and what each part holds
  - file order
  - the explicit `Changed` and the told-only `Update`
  - `Read` reporting the real resource
  - the test shape
  - starting from the template
  - releasing
- `docs/README.md`, `docs/plugin-developer-guide.md` and the README link to it and to the template.
- `CHANGELOG.md` records the feature.

**xcl-website.**
- The shared jumppad-labs release signing public key is served at `/keys/jumppad-labs-releases.asc`, with fingerprint `15BD A684 3A1F A0EA D1AA  5190 F775 DA00 AFD4 B502`.
- A new Guides page, `/plugin-template/`, covers the layout and how to start, build, run, release, install and verify a plugin from the template. It is in the Guides navigation and linked from the registries and plugins example pages.

## Why it matters

Plugin authors start from a working, idiomatic plugin instead of hand-copying examples. The project now has one documented layout that the template, the examples and future jumppad ports all follow. A plugin made from the template is checked on every change and publishes signed releases for every platform that applications install with one line through the GitHub registry. The template is a registered project repository, so later changes to the plugin contract are planned into it too.

## Deviations from the plan

- **Release deferred.** The human task "Publish the template's first signed release" was deferred at the user's choice until after the merge and push to the template's `main`. It is the first manual check in the test plan. The release automation was instead verified locally:
  - the asset names match the contract exactly;
  - the workflow's gpg import and sign commands produce a signature that verifies;
  - the empty-key guard fails;
  - xcl's GitHub registry, pointed at a local fake of the releases API, installed, verified, applied, re-planned with no changes and destroyed the sample;
  - the registry refused the release under a different key.
- **staticcheck.** It is pinned at v0.8.1, which needs Go 1.26 or later, while the module's minimum is Go 1.25. The CI lint step therefore sets `GOTOOLCHAIN=auto`.
- **Dependencies and moved paths.**
  - `go.mod` gained indirect requirements once the tests imported xcl. xcl stays pinned at v0.1.1.
  - The plan's references to `example/plugin/.mockery.yml` and `example/plugin/Makefile` were followed from their new homes under `example/plugin/plugins/docker/`, where the sibling docker-layout spec had moved them.
- **Extras and ordering.**
  - A few extra unit tests were added.
  - The release workflow also runs the tests before building.
  - The xcl docs task ran before the human release task, which nothing depended on.
- **Changelog format.** The CHANGELOG entry uses `None.` under Breaking, to match the existing entries.

## Answered open questions

- A state reader that registers only the plugin binary and imports only `entities` decodes applied notes into `entities.Note` with `xcl.FindByType` after `Load()`.
- A gpg `--armor --detach-sign` signature from an Ed25519 key verifies with the registry's OpenPGP library. This was confirmed locally with a throwaway key. The live check against the real release is in the test plan.
