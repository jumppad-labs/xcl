# Sensitive values: references and secrets

## What was built

A Go field can be declared sensitive by giving it the type `types.Sensitive[T]`, for application-registered types and plugin types alike. The type protects itself: every `fmt` verb, `log/slog`, `encoding/json`, text marshalling and templates show the fixed marker `(sensitive)`, and only `Reveal()` returns the real value. `types.NewSensitive` builds one.

Inside configuration, sensitivity travels as a cty mark, applied and removed through a new generic wrapper hook in the copied `gocty` library, so references, interpolation, functions, module inputs and outputs all carry it. A new validation stage predicts statically which parts of each expression are sensitive and rejects any sensitive part landing in a field that is not declared sensitive, naming the field, so `Validate` and `Apply` refuse such configurations before anything is created; at walk time a marked value meeting a plain field is an error rather than a panic. Outputs hold exactly their sensitive parts as `types.Sensitive` values and record them in `types.Output.SensitivePaths`, so they read back the same after a reload. Converting or looking up an entity into a Go type whose matching field is plain fails with `ErrTypeMismatch`, naming the field in the new `TypeMismatchError.Field`.

State and plugins see real values through a new internal encoder (`internal/wire`) used by provider calls, change detection, the host state callback, query conversion and both state save sites, which now hand each store `json.RawMessage` records. Event data at both levels is re-encoded with standard JSON and shows the marker. Function errors replace sensitive argument text with the marker. Configuration text and the resource printer show the marker by default, with `xcl.RevealSensitive()` and `logger.WithRevealSensitive(true)` to show real values; a value read back from the marker always shows the marker. Plugin types may use seven supported `Sensitive` instantiations; any other fails plugin loading naming the type and field.

The application-config and plugin examples declare their passwords sensitive and reveal them only where used. The README, plugin developer guide, state, plugins and modules docs, changelog and the documentation site (a new Sensitive values page and refreshed example pages) describe the feature. An end-to-end leak suite checks every output path for a known secret.

## Why it matters

Secrets in an xcl configuration used to appear in plain text wherever xcl or the application printed, logged or reported them. Application developers, plugin authors and their users now stop leaking secrets by accident, while state and providers still get the real values they need.

## Deviations from the plan

- The configuration-text redaction (`gohcl.EncodeOptions.ReplaceMarked`, `xcl.RevealSensitive()`) landed with the event-data task, because converting event data to text needed it. A public `types.RedactedMark` (applied through a generic `gocty.Wrapper.ExtraMarks`) marks values read back from the marker so revealing still shows the marker.
- `gohcl` attribute-decode diagnostics now name the attribute (generic, recorded in `UPSTREAM.md`).
- `types.Output` gained `WrapSensitivePaths()` and a `Format` method; the leak suite found that `fmt` of an output reached the real value through `CtyValue` by reflection.
- The plugin registry checks every plugin type can be rebuilt when its host is added, so an unsupported instantiation fails loading.
- Tests that saved state themselves now encode with `parser.EncodeForState`; a types package test moved to an external test package to avoid an import cycle.
- `All` and `Decode` cannot reach a plain-field target type (registered types convert only to themselves), so the field guard is tested through `Find`, `FindByType` and `As`.
- The plugin example's configured passwords were changed to distinctive values so the no-secret tests are meaningful.
- The external plugin is exercised through host-level Create and Read rather than a full apply.
