# User-written depends_on lists are kept as written

## What was built

A `depends_on` list now holds exactly what the configuration author wrote, after parsing, after applying and when loaded back from saved state. xcl no longer copies the dependencies it works out from references into it, so state, plugin calls and event data carry the author's list as written, and configuration text (`EncodeEntity` / `EncodeSavedEntity`) shows a written list exactly as written and no list when none was written.

Ordering still honours every dependency. All dependencies, references and written `depends_on` entries alike, live in each entity's `Meta.Links`. One graph builder, `buildDependencyGraph` in `internal/parser/dag.go`, now orders both creation and destruction from those links. Destroy builds the same graph from the links each resource saved, resolved against the whole working state with only edges between the entities being destroyed, and walks it backwards; a parent module missing from state is ignored rather than refusing the destroy. The separately recorded `Meta.Parents` / `meta.parents` was removed, since nothing reads it any more. A `depends_on` entry reaching inside a module is still rejected by the module boundary check, because written entries stay in the links.

Changes, all in `xclconfig` unless noted:

- The create graph reads `Meta.Links` instead of `DependsOn`.
- Destroy, both `Parser.Destroy` and `Apply`'s removal phase, uses the shared builder; the destroyer gained an address parser.
- `types.Meta.Parents` was removed, along with its golden-schema entries. Tests that read it now read the graph built from saved state.
- `types.AppendUniqueDependency` was replaced by `types.AppendUniqueLink`, which appends to links only. The parser sets `DependsOn` to the written strings.
- Configuration text writes `depends_on` when the list is non-empty.
- README, CHANGELOG (with a **Breaking** list), and the state, overview, parser lifecycle and plugin developer guides were updated, with content tests guarding the README and CHANGELOG text.
- `xcl-website`: the configuration-text guide gained a "Dependency lists" section with an example.
- The knowledge entry `learnings/depends-on-mirrors-links.md` was rewritten to describe the new split.

## Why it matters

Before this change, the author's dependency list was mixed with dependencies xcl worked out, so it could not be shown or round-tripped faithfully. Authors now see their own list in state, events and configuration text, and create and destroy order rest on a single source of dependencies with a single builder.

## Breaking changes

- `DependsOn` holds only the written list. Read `Meta.Links` for every dependency.
- `types.AppendUniqueDependency` is replaced by `types.AppendUniqueLink`.
- `types.Meta.Parents` is removed, and saved state no longer carries `meta.parents`. Older state carrying it still loads, with the key ignored, and is ordered from its links.
- Configuration text includes `depends_on` when one was written.

## Deviations from the plan

- `buildCreateDAG` temporarily kept the mirror and the parents recording as a prelude before the shared builder. Both were removed in later tasks, as planned.
- An extra graph-level test pins module-relative link resolution from saved state, because the call-order test for it could pass by chance. Concurrent walks make call order between independent resources nondeterministic.
- The module-boundary `depends_on` tests from the earlier spec already covered the regression, so none were duplicated.
- The knowledge entry kept its path, and only its title changed.
- The plan's open question is resolved: the walk's decode writes exactly the strings the parser recorded, so no change to `internal/xcl` was needed.
