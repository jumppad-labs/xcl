# Python pretty logger (`xcl.prettylog`)

## What was built

Python programs that use xcl now have a ready-made pretty logger, `xcl.prettylog`, set up in one line on either client:

```python
cfg = xcl.Config(on_event=xcl.prettylog.handler(sys.stderr, xcl.prettylog.level_from_env()),
                 event_data=xcl.EventDataLevel.PROCESSED)
```

- **Event lines.** Each event at or above the chosen level is one line in exactly the layout Go's example pretty logger (`example/prettylog`, charmbracelet/log v0.4.2) writes: Kitchen time, four-letter level, message, then source, operation, phase, resource, type, file, duration, error and the sorted details as `key=value`, with Go's quoting, escaping, multi-line layout and value formatting (floats, durations, lists, maps). The source, operation and resource are highlighted. Colour comes from the package's printing support (`xcl.highlight`): terminal colour when the stream is a terminal and `NO_COLOR` is unset, plain text otherwise, or any formatter passed as `formatter=`.
- **Created resources.** At info and below, each created resource's configuration, including values the provider filled in, is written indented beneath its `create success` line as soon as it is reported, rendered from the event's saved record through the configuration that delivered the event. Variables, outputs and modules are skipped silently; any other render failure gives one `WARN unable to show configuration` line and the run continues. When the configuration has no event data, one line (once per handler) says to create it with `event_data=xcl.EventDataLevel.PROCESSED`.
- **Configuration mistakes.** At every level, a configuration mistake's report (summary, file and line, block and field, numbered source lines with the fault marked, detail) is written beneath its error line, once per problem, counted per configuration.
- **Levels.** `level` is a standard `logging` level (info by default); `level_from_env()` reads `XCL_LOG_LEVEL` (debug, info, warn, error, any case; info otherwise). Above info only event lines and reports are written.
- **Existing logging.** `handler(logger=...)` sends the same text through an application's logger, one record per event at the event's level and time, carrying the logging bridge's structured fields.
- **Asyncio ordering.** `xcl.aio.Config` now delivers events to `on_event` one at a time and in order through one consumer per operation, as Go and the synchronous client do; state-store and function tasks stay concurrent. This also fixes `xcl.logging_handler`'s ordering under asyncio.
- **Plumbing.** Events carry a private reference to the configuration that delivered them; both configuration flavours remember their event data level and offer a private blocking render of a saved record that never queues behind the asyncio poll; the logging bridge's level, message and record rules are shared helpers.
- **Proven against Go.** xcl's parity program gained a `pretty_log` stage that runs Go's real example on every fixture whose apply succeeds, and xcl-python's parity program records the same through `xcl.prettylog`; the existing comparison now holds the Python pretty output to Go's on every shared fixture, and it matches.
- **Documentation.** The xcl-python README has a "Pretty logging" section and a corrected asyncio section; PARITY.md pairs Go's example with `xcl.prettylog`; xcl.dev's events page shows `xcl.prettylog` in place of a hand-written Python receiver.

## Why it matters

A Python program had no ready-made way to watch what xcl does, and even a hand-written handler could not show what each resource became. Now one line gives the same readable, coloured log Go's examples show, with each created resource and each configuration mistake shown as it happens.

## Deviations from the plan

- The human release task was descoped to a person after the merge (decided for the epic); the steps, including the GitHub release-notes line about asyncio's in-order delivery, are in the plan's descoped list and the test plan.
- The logging bridge already had private `_level`/`_message`/`_extra` helpers; they were renamed to the plan's shared names and `event_record` was added.
- The shown-problem count is kept per configuration, not per handler, so configurations sharing a handler never hide or repeat each other's reports; in logger mode the handler does nothing for an event its logger would drop.
- The engine-backed test module is `tests/integration/test_prettylog_engine.py` (a module basename must be unique across the test directories).
- The README section sits under "Logging"; the PARITY.md pairing is its own table.
- The Go parity stage strips colour codes rather than setting `CLICOLOR_FORCE`.
