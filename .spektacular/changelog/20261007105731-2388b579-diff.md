# Diff: report what an apply would change

## What was built

`Config.Diff(paths, options...)` reports what `Config.Apply` would do with the same configuration, and does none of it. It returns a `*diff.Diff` from the new public `diff` package, which contains:
- a summary of how many resources would be created, updated, replaced, deleted or left unchanged;
- every resource that would change, sorted by address, with its action;
- for each of those resources, every configured value that would change. Each change has a structured path (`image`, `port[0].local`, `env["LOG_LEVEL"]`) and its before and after values.

`json.Marshal` of the result is the machine-readable format fixed by the design `config-diff.md`.

**How the diff is produced:**
- It runs as its own `diff` operation through the same wrapper as Apply, so callers get the same start, finish, lifecycle and log events.
- It reuses the apply walk. It parses and validates exactly as Apply does, and records removed provider-backed resources as deletes. It then walks the dependency graph in a diff mode.
- Saved created/updated resources are read and compared through their providers using the same refresh step Apply now uses, which was split out of the apply read path. So drift shows up as an update, and a resource that has vanished shows up as a create. Failed and destroy_failed resources are reported as replace.
- It never calls Create, Update or Destroy, never writes state, and leaves `Config.Entities()` untouched.
- A provider error fails the diff with an error that names the resource and still matches the provider's error.

**Unknown values:**
- Values only known once an apply has run are reported with `unknown: true`. These are the computed fields of any resource being created, replaced or updated.
- They are carried into dependents through an unknown-aware evaluation context and a diff decoder. The decoder substitutes placeholders in a copy of each body, because Go fields cannot hold unknowns.
- A saved resource that depends on an unknown value is reported as update and is not read.

**Sensitive values:** these are masked, with neither value present, unless `diff.RevealSensitive()` is given. A whole added or created value that holds a secret is split so that the secret stands alone.

## Why it matters

Applications and tools built on xcl can find out, before running an apply, what it would do:
- which resources would be created, changed, replaced or deleted;
- exactly which values would change, including drift in real infrastructure.

They can inspect this result directly in Go or as JSON, and they never see a secret unless they ask for it.

## Deviations from the plan

- **Computed values of updated resources are unknown.** The end-to-end suite found an apply updating `app.web` after a redis port edit, and the diff had not listed it: redis's Update recomputes the `connection_string` that `app.web` references. The user revised the design. Every computed field of a resource reported as update is now unknown, so its dependents are reported as update with that value unknown and get no provider call. A task was added for this.
- **The parity contract changed.** The spec's success metric "diff matches apply for every scenario" is superseded by a new contract:
  - an apply never changes a resource the diff did not list;
  - any listed resource the apply leaves alone was listed with at least one unknown value.

  The diff may over-report and never under-reports.
- **The provider override is a separate spec.** A provider method that says which computed fields an update changes (`ComputedChanges`, its gRPC RPC, and the Docker network example) moved to a separate spec in this epic.
- `Parser.walk` keeps its signature and delegates to a new `walkWith` that takes a prepared lifecycle, instead of taking extra arguments.
- Outputs and module variables carry unknowns natively as cty values, so no unknown paths are recorded for them separately.
- The credential test fixture's password is sensitive because it flows into a `types.Sensitive` field. The repo has no `sensitive = true` variable syntax.
- The "state cannot be loaded" test uses a corrupt state file rather than `UnknownTypesError`.
