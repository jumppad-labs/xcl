# Changelog

## 20260922061954-event-based-logging

xcl no longer writes any output of its own, and no longer calls `log.SetOutput` or otherwise touches the standard library's global logger. Everything it and its plugins report, each lifecycle step, plugin discovery and loading, warnings, errors and the messages plugins log, is one stream of events delivered to the receiver set with `xcl.WithEventHandler`; with no receiver xcl is silent. The event type moved to a new leaf package, `events`, and `xcl.Event` and `xcl.EventHandler` are now aliases of `events.Event` and `events.Handler`. `Event` gains `Time`, `Source` (`core` for xcl, otherwise the plugin's name) and `Meta` (details; a log message's level and text are under the reserved keys `level` and `message`), and new operations (`validate`, `apply`, `discover`, `load`, `events`) and phases (`log`, `blocked`) are defined as constants. `events.SlogHandler(*slog.Logger)` writes the stream to `log/slog` in one line of setup, and `example/prettylog`, a slog handler built on charmbracelet/log, replaces `example/eventlog` in the examples.

Each `Validate`, `Apply` and `Destroy` now starts with its own `start` event and ends with a `success` or `error` event carrying the error it returns. Every failure that is returned is also emitted as an error event, including each problem validation finds. The receiver is called one event at a time, in emit order, on the goroutine that called `Validate`, `Apply` or `Destroy`, and every event has been delivered before the call returns. Emitting never waits for the receiver: undelivered events are held in a bounded buffer, `xcl.WithEventBufferSize` (default `xcl.DefaultEventBufferSize`, 1024), and when it is full emitting waits rather than dropping, after which the receiver gets one `events`/`blocked` event saying how long it waited. A panic in the receiver is not recovered: xcl starts no new provider call, lets the calls in progress finish (providers are called with a context that is never cancelled), saves state, and then the panic continues with its original value and stack.

Providers log through `plugins.Logger(ctx)`, a logger xcl puts in each provider call's context, bound to the resource, its type, its file and the step, and named after the plugin. Messages arrive between the call's `start` and its `success` or `error`, the same for in-process and external plugins. The logger given to `Init` is plugin scoped, for messages written outside a call; in-process provider `Init` loggers add the detail `provider=<block type>`. External plugins tag each call with an ID, sent as `xcl-call-id` gRPC metadata and returned in `LogRequest.call_id`, so the host can give each message its call's resource and receiver; detail values cross the process boundary as text and are re-typed where they parse as a number or boolean. go-plugin's own messages become log events with the detail `component=go-plugin`, routed to the operation in progress. The changed-configured-value warning is now a `warn` log event with the field path in `Meta["field"]`.

The plugin registry loads plugins lazily. Registering only records a plugin, and plugins are discovered, started and checked at the start of the first `Validate`, `Apply` or `Destroy`, once per registry however many Configs share it, reported as `discover` and `load` events. A registered plugin that fails to load fails that operation with an error matching `xcl.ErrPluginLoad`, whose `*xcl.PluginLoadError` names the plugin. A discovered binary that fails to load is rejected (a `load` error event with `rejected=true`) unless every discovered plugin fails. A type name clash between plugins, or with a registered or builtin type, fails the load; `RegisterType` still reports a clash with a builtin, registered or already loaded type straight away.

One known exception to xcl's silence remains: when an external plugin is stopped within milliseconds of starting, go-plugin v1.6.3 writes `[ERR] plugin: plugin acceptAndServe error: broker closed` to standard error through the standard library logger. It is outside xcl's control.

**Breaking:**
- `registry.NewPluginRegistry()` takes no logger.
- `DiscoverAndLoadPlugins(logger, dirs, pattern)` is replaced by `DiscoverPlugins(dirs, pattern)`, which only records the directories to search.
- `RegisterPlugin`, `RegisterPluginWithPath` and `DiscoverPlugins` no longer start or check plugins. A missing or broken plugin, and a plugin type name clash, is reported by the first `Validate`, `Apply` or `Destroy` instead of at registration; match load failures with `errors.Is(err, xcl.ErrPluginLoad)` and `*xcl.PluginLoadError`. Code that loads a state store directly should call the registry's `Load` first.
- `Plugin.SetLogger` and `PluginBase.SetLogger` are removed. Providers log through `plugins.Logger(ctx)` during a call; a logger kept from `Init` is plugin scoped and carries no resource.
- Every `PluginEntityProvider` and `PluginHost` lifecycle method (`Validate`, `Create`, `Destroy`, `Read`, `Update`, `Changed`) takes a `context.Context` first.
- The `plugins.Logger` type alias is removed, use `logger.Logger`. `plugins.Logger` is now the function `plugins.Logger(ctx)`.
- `plugins.NewDirectPluginHost(emit, state, plugin)` and `plugins.NewGRPCPluginHost(emit, state)` take an `events.Emit` instead of a logger. The test helpers `InProcessPluginSetupWithLogger` and `ExternalPluginSetupWithLogger` are replaced by `InProcessPluginSetupWithEmit` and `ExternalPluginSetupWithEmit`.
- The logger implementations are removed: `logger.NewStdOutLogger`, `NewStdOutLoggerWithOptions` and `NewTestLogger`. The only implementation is `logger.New(emit, base)`, which emits log events, plus `logger.Nop()`. `logger.WithTag` now adds an event detail, and `logger.WithSource` sets an event's source.
- The `event=<name>` text line format introduced by `20260919152915-destroy-cycle` is gone, as are the framework's `calling provider` log line (the lifecycle `start` event replaces it) and the `plugin loaded` line (loading is now a `load` event).
- `LogRequest` in `plugins/plugin.proto` gains `call_id`. External plugins must be rebuilt against this version.

## 20260919152915-destroy-cycle

`Config.Destroy` now works; it used to report success while doing nothing. It needs no configuration: it destroys everything in the saved state through the providers, dependents before what they depend on. The order comes from a new `meta.parents` field that every saved resource now records: the IDs of the resources it depends on, resolved when it was applied. The state is saved after every resource, so an interrupted destroy resumes where it stopped. A resource whose destroy fails stays in the state as `destroy_failed`, together with everything it depends on. Unrelated resources are still destroyed, the error names every failure, and running `Destroy` again retries it. Variables, outputs, modules, disabled blocks and registered types never reach a provider. Destroying when nothing was saved succeeds and writes nothing. Destroy events (`destroy` with `start`, `success` or `error`) reach `xcl.WithEventHandler` like every other event.

`Apply` now destroys blocks that were removed from the configuration, children first, before it creates or changes anything. If one of those destroys fails, the apply stops before creating or changing anything and keeps the resource as `destroy_failed`, and the next apply retries it first. Applies that remove nothing behave as before.

Both examples now keep their state in a file, and apply and then destroy the shared configuration.

Every log line now leads with its event, `event=<name>`, ahead of the `plugin=`/`provider=` tags: `StdOutLogger` and `logger.WithTag` move an `event` argument to the front, and a message logged without one is written as `event=log`. The framework's own lines carry events too: `calling provider` logs `event=<operation> resource=<id>` (it used to log `operation=` and `id=`), `plugin loaded` is `event=load`, go-plugin's logs are `event=go-plugin`, plugin discovery is `event=discover` and the changed-configured-value warning is `event=configured_value_changed`.

**Breaking:**
- Applying a configuration with no blocks fails with `xcl.ErrEmptyConfiguration` and changes nothing. Use `Destroy` to remove everything.
- `FileStateStore.Load` fails with `state.UnknownTypesError`, naming every saved type that isn't registered. It used to silently drop those resources, so the next save erased them from the state. Register every type and plugin before loading state.
- Removed blocks are now destroyed through their provider.
- `destroyed` is no longer saved, because destroyed resources leave the state.

## 20260919120639-config-only-types-and-examples

Added configuration-only block types. `PluginRegistry.RegisterType("postgres", &PostgreSQL{})` registers a plain Go type that embeds `types.ResourceBase` as a block type, with no plugin or provider. Its blocks decode into your own Go type, take part in references, dependency ordering, modules and disabled handling, are saved to state and reloaded as that type, and never trigger a provider call. Type names are now unique across builtins, registered types and plugins: registering or discovering a type or plugin whose name is already taken fails with a `*registry.TypeNameClashError` naming the type, where previously the first plugin silently won. **Breaking:** `Querier[T].FindResourcesByType` now takes the type name (`FindResourcesByType("postgres")`) and returns exactly that type's resources, which it previously never did. Registered types are returned as the value held in state. `Validate` now rejects attributes and blocks that a resource's type doesn't have, for every resource type, instead of failing later during `Apply`. `xcl.WithEventHandler` exposes the lifecycle events (`create`, `read`, `changed`, `update`, `destroy`, each with `start`, `success` or `error`) that were previously only available on the internal parser, plus a new `parse` event for every block as it is read, with a `success` or an `error` and the `File` it came from, fired by both `Apply` and `Validate`. The stale example was replaced with a shared configuration and Go types used by two tested programs, `example/configonly` and `example/plugin`. Everything a plugin logs is now tagged at the start of the message with `plugin=<name>` (the Go type name in-process, the binary name for an external plugin), and provider logs also with `provider=<block type>`, so plugin logs can be told apart from the host's; `logger.WithTag` does the tagging. go-plugin's own logs for external plugins, which went straight to stderr in their own format, now go through the host's logger with the same tags at debug (trace messages are dropped, warnings and errors keep their level). In-process and external plugins log the same framework messages at debug, `plugin loaded` and `calling provider`, and the plugin-side gRPC server no longer logs its own info messages. The plugin example uses an in-process plugin for `postgres` and an external, compiled plugin for `app`, and logs from each provider method. Both examples log every event, parse events included, through a shared `example/eventlog` handler.

## 20260714080036-restore-module-support

Restored support for `module` blocks in configuration files. You can now package a set of resources into a reusable module, instantiate it multiple times with different variable values, and nest modules inside other modules. Each module instance produces its own independent set of resources, resources inside a module can reference each other and the module's own variables, and a module instance can be disabled (which also disables all of its resources) while a resource inside a module can still independently control its own disabled state. Only local, relative-path module sources are supported; remote or URL-based module sources are not part of this change.
